# Spec review items

Open decisions for the gRPC spec draft in `grpc/doc/spec/`: **41** items, grouped by type (spec divergences first, then doc conflicts, language divergences, judgment calls, and language bugs last) and, within each type, sorted by position in the spec (by full section number; LB policy docs follow their parent section, and appendices come last). Each item is named for the system it concerns, and each matches an inline `<!-- REVIEW(...) [<name>]: ... -->` comment at the linked line in the spec.

The type in each header is one of:

- **language bug** — the spec matches at least one language (usually the majority or the gRFC); other languages deviate.
- **language divergence** — languages differ and there is no clear right answer yet.
- **spec divergence** — no language implements what the spec says.
- **judgment** — a design choice that implementation behavior doesn't settle.
- **doc conflict** — the spec disagrees with a gRFC or existing doc on a point where the implementations don't settle it (or agree with the spec).

Sections: [Language divergences](#language-divergences-19) · [Judgment calls](#judgment-calls-6) · [Language bugs](#language-bugs-16)

Every item quotes the prior documentation (gRFCs, older `grpc/doc` text, proto comments, or the pending call-semantics and client-channel PRs) that bears on it, or says that no prior documentation covers it. Resolved items are in [resolved_items.md](resolved_items.md); implementation bugs are in [bugs_go.md](bugs_go.md), [bugs_java.md](bugs_java.md), [bugs_cpp.md](bugs_cpp.md), and documentation bugs in [bugs_docs.md](bugs_docs.md).

## Language divergences (19)

### RETRY-7. Case-3 transparent retry after a configured retry (language divergence)

Languages differ on whether the one "reached the server library but not the application" transparent retry can happen after a configured retry.

- **Where:** [4.12.8 Transparent Retries](04-client-channel/12-retries.md#8-transparent-retries) in `04-client-channel/12-retries.md`
- **Current spec:** Case 3: "Transparently retried **once** per RPC. If that retry also fails this way, the failure goes to the configured retry policy." It does not say whether it can happen on a later attempt.
- **Findings:**
  - C++: allowed on any uncommitted attempt, at most once per RPC (`sent_transparent_retry_not_seen_by_server_`). ([retry_filter_legacy_call_data.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/client_channel/retry_filter_legacy_call_data.cc#L1111-L1122))
  - Java: `REFUSED` is retried transparently only if `noMoreTransparentRetry` is still false. Any non-transparent attempt failure sets it, so after the first configured retry REFUSED goes to the retry policy. (`MISCARRIED`, case 2, is unlimited up to 1000.) ([RetriableStream.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/RetriableStream.java#L962-L996))
  - Go: `cs.firstAttempt && unprocessed` allows it only on the very first attempt; `firstAttempt` is cleared after any retry. ([stream.go](https://github.com/grpc/grpc-go/blob/v1.82.0/stream.go#L702-L705), [stream.go](https://github.com/grpc/grpc-go/blob/v1.82.0/stream.go#L791))
- **Prior documentation:** gRFC A6, "Transparent Retries": "If the RPC reaches the gRPC server library, but has never been seen by the server application logic (the third case), the client library will immediately retry it once. If this fails, then the RPC will be handled by the configured retry policy." It does not decide the question.
- **Decision:** (a) once per RPC, on any attempt (C++, current wording); (b) only before the first configured retry (Java, Go); or (c) leave it implementation-defined.
- **Recommendation:** (a). A REFUSED_STREAM on a later attempt (for example during a server's graceful shutdown) is just as safe to retry, and the once-per-RPC cap already bounds the extra load. State it outright. Bugs (low): Java and Go: case-3 transparent retry not available after a configured retry.
- **Why this rank:** A rare edge case. The effect is that a configured retry attempt is used up (or the RPC fails) instead of retrying transparently.

### TRANSPORT-6. Ping enforcement: Go and C++ measure from the last PING received, not the last valid one (language divergence)

The spec's ping-enforcement pseudocode (from A8) updates `last_valid_ping_time` only for an acceptable PING. Go and C++ update their timestamp on every PING received, including PINGs that earn a strike. Java follows the pseudocode, but its `epoch` is the transport's creation time.

- **Where:** [5.2.2.7.2 Ping Enforcement](05-server/02-transports/02-http2.md#72-ping-enforcement) in `05-server/02-transports/02-http2.md`
- **Current spec:** `if ok: last_valid_ping_time = now() else: ping_strikes += 1 …`; on HEADERS or DATA sent, `last_valid_ping_time = epoch`.
- **Findings:**
  - C++: `last_ping_recv_time_ = now` before the comparison, so it is updated for every PING ([ping_abuse_policy.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/ext/transport/chttp2/transport/ping_abuse_policy.cc#L53-L62)). The reset sets it to `InfPast`, which matches `epoch`.
  - Java: updates only on a valid PING in `KeepAliveEnforcer` (shared by Netty and OkHttp servers) ([KeepAliveEnforcer.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/KeepAliveEnforcer.java#L57-L71)). But `epoch = ticker.nanoTime()` at construction ([L51-L52](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/KeepAliveEnforcer.java#L51-L52)), so after a reset, a PING within `PERMIT_KEEPALIVE_TIME` of connection start counts as a strike.
  - Go: `defer t.lastPingAt = now` runs for every PING. After a reset, the next PING is accepted unconditionally ([http2_server.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/transport/http2_server.go#L892-L917)).
  - Effect: a client pinging steadily a bit faster than allowed is disconnected on its 4th PING in Go/C++. Under the pseudocode, only every other PING is a strike, so it lasts about twice as long.
- **Prior documentation:**
  - gRFC A8, Server Enforcement: "If either verification failed, ping\_strikes++ … otherwise `last_valid_ping_time = now()`" and "set `last_valid_ping_time = epoch`". This matches the spec.
  - doc/keepalive.md: "If the time between successive pings is less that than this time, then the ping will be considered a bad ping". This describes the C++ behavior: successive PINGs, valid or not.
- **Decision:** (a) keep the A8 algorithm and file Go/C++ bugs, (b) allow measuring from the last PING received (either algorithm conforms), (c) adopt the Go/C++ algorithm.
- **Recommendation:** (b). Both variants are stricter or looser only for clients that are already misconfigured. A8 calls it a "Suggested algorithm", and doc/keepalive.md describes the C++ variant. Say that `epoch` means "earlier than any possible PING". No bugs, unless (a) is chosen.
- **Why this rank:** Affects only misbehaving clients. The spec pseudocode currently matches only one implementation.

### SECURITY-20. `AuthContext` API shape, property names, and client-side availability timing (language divergence)

C++ exposes a string-keyed multimap (`grpc::AuthContext`) with the property names in §6.2. Java and Go expose typed TLS session objects (`SSLSession`, `credentials.TLSInfo`) without string property keys, and Go fills the unary client `Peer` only when the RPC completes.

- **Where:** [6.1.6 AuthContext and Peer Identity](06-security/01-security-model.md#6-authcontext-and-peer-identity) in `06-security/01-security-model.md`
- **Current spec:** §6.1 defines the AuthContext as a multimap of auth properties plus a peer identity property name, reachable "on the client through the call after the response headers arrive". §6.2 says the property names (`transport_security_type`, `x509_*`, `peer_*`, `ssl_*`) "are part of the public API. Implementations MUST use these names when they expose the information." §8 requires the server call API to "iterate all properties, look up properties by name, get the peer identity property name, get the peer identity, and check whether the peer is authenticated", and requires the client call API to "give access to the AuthContext of the connection an RPC used, once response headers have been received".
- **Findings:**
  - C++: `grpc::AuthContext` provides the multimap, `GetPeerIdentity`, `GetPeerIdentityPropertyName`, and `IsPeerAuthenticated` ([secure_auth_context.cc L30-L97](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/cpp/common/secure_auth_context.cc#L30-L97)). The TLS properties are filled from the TSI peer ([ssl_utils.cc L295-L362](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/credentials/transport/tls/ssl_utils.cc#L295-L362)). The `ssl_tls_version` and `ssl_requested_server_name` name constants are defined only in the internal `tls_utils.h`, not in the public `grpc_security_constants.h`. `ssl_requested_server_name` is added whenever `SSL_get_servername` returns a name, on both the client and the server ([ssl_transport_security.cc L2349-L2352](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/ssl_transport_security.cc#L2349-L2352)).
  - Java: the public API is `Grpc.TRANSPORT_ATTR_SSL_SESSION` (`javax.net.ssl.SSLSession`) on transport and call `Attributes` ([ProtocolNegotiators.java L735-L740](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/ProtocolNegotiators.java#L735-L740)). `ATTR_SECURITY_LEVEL` is in `io.grpc.internal.GrpcAttributes`. There is no `AuthContext` multimap, no string property keys, and no peer identity property name. On the client, `ClientCall.getAttributes()` "May only be called after `Listener#onHeaders` or `Listener#onClose`" ([ClientCall.java L277-L287](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/api/src/main/java/io/grpc/ClientCall.java#L277-L287)).
  - Go: `peer.FromContext` returns `credentials.TLSInfo{State tls.ConnectionState, SPIFFEID *url.URL}` on the server and from a client stream's context ([tls.go L41-L46](https://github.com/grpc/grpc-go/blob/cbf30c4130/credentials/tls.go#L41-L46)). For unary client RPCs, `grpc.Peer(&p)` fills `Peer` only in `PeerCallOption.after`, when the RPC finishes ([rpc_util.go L309-L331](https://github.com/grpc/grpc-go/blob/cbf30c4130/rpc_util.go#L309-L331)). There are no string property keys.
- **Prior documentation:**
  - `doc/server_side_auth.md`: "NOTE: This document describes how server-side authentication works in C-core based gRPC implementations only. In gRPC Java and Go, server side authentication is handled differently."
- **Decision:** (a) describe the multimap and property names as the conceptual model, require them (`MUST`) only for implementations that expose a string-keyed property API, require every implementation to give access to the peer certificate chain, peer identity, security level, and TLS session information in an idiomatic form, and require client-side availability no later than call completion; or (b) require every implementation to expose the C-core property multimap and names (bugs on Java and Go).
- **Recommendation:** (a). `doc/server_side_auth.md` is scoped to C-core, and Java and Go use their platform TLS types. Under (a), also mark `ssl_requested_server_name` as set on both sides, or file a C++ low bug.
- **Why this rank:** A core security section prescribes the C-core API structure as a universal `MUST`, but two of the three implementations don't follow it.

### TLS-20. Server mTLS trust store when no roots are configured (language divergence)

When a TLS server verifies client certificates but has no root certificates configured, C++ uses no trust anchors, so presented client certificates fail verification. Java and Go fall back to the system default root CAs.

- **Where:** [6.2.5 Client Certificates and Mutual TLS](06-security/02-tls.md#5-client-certificates-and-mutual-tls) in `06-security/02-tls.md`
- **Current spec:** "A server that verifies client certificates MUST have roots configured: there is no default trust store for client certificates."
- **Findings:**
  - C++: the server handshaker factory gets only the configured `root_cert_info` and loads no default root store. The client side uses the default roots ([ssl_utils.cc L497-L535](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/credentials/transport/tls/ssl_utils.cc#L497-L535), [tls_security_connector.cc L844-L860](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/credentials/transport/tls/tls_security_connector.cc#L844-L860)).
  - Java: when neither trust managers nor root certificates are set, `ProtocolNegotiators.from(ServerCredentials)` configures no trust manager ("`// else use system default`"), so `ClientAuth.OPTIONAL`/`REQUIRE` verifies against the JVM default trust store. The `TlsServerCredentials.Feature.MTLS` Javadoc says: "If no root certificates are provided the trust manager will default to the system's root certificates." ([ProtocolNegotiators.java L206-L210](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/ProtocolNegotiators.java#L206-L210), [TlsServerCredentials.java L205-L211](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/api/src/main/java/io/grpc/TlsServerCredentials.java#L205-L211)).
  - Go: `advancedtls` server options with no root options and `RequireClientCert` set use `x509.SystemCertPool()` "as the last resort" ([advancedtls.go L394-L404](https://github.com/grpc/grpc-go/blob/cbf30c4130/security/advancedtls/advancedtls.go#L394-L404)). With `credentials.NewTLS`, `crypto/tls` verifies client certificates against the system roots when `ClientCAs` is nil.
- **Prior documentation:**
  - Not covered for standalone TLS server credentials. For xDS, gRFC A29 says: "Note that if `require_client_certificate` is true, and if no `CertificateValidationContext` is provided, gRPC will NACK the LDS resource."
- **Decision:** (a) let standalone TLS server credentials either require explicit roots or fall back to the system trust store (`MAY`), recommend explicit roots (`SHOULD`), and keep the xDS requirement in `09-xds/09-security.md`; or (b) keep "there is no default trust store for client certificates" and file bugs against Java and Go.
- **Recommendation:** (a). Java documents the fallback in its public API (`TlsServerCredentials.Feature.MTLS`), and in Go it is the standard `crypto/tls` behavior. If (b) is chosen, the bugs are Java (medium) and Go (medium).
- **Why this rank:** Security-sensitive trust-anchor behavior. Two of the three implementations accept client certificates from public CAs when no roots are configured, which the spec forbids.

### TLS-21. Present-but-invalid CRL: fail closed or `Undetermined` (language divergence)

When the CRL provider returns a CRL for the certificate's issuer but the CRL fails validation (issuer mismatch, missing `cRLSign`, bad signature), the spec and Go treat the status as `Undetermined`, which allows the connection under the default fail-open policy. C++ fails the handshake.

- **Where:** [6.2.9.2 Revocation Status](06-security/02-tls.md#92-revocation-status) in `06-security/02-tls.md`
- **Current spec:** The status table defines `Undetermined` as "No CRL was found for the issuer, or no CRL could be validated". `Undetermined` becomes `Revoked` or `Unrevoked` according to the application's policy.
- **Findings:**
  - C++: `CheckCertRevocation` treats a CRL that the provider did not find as unrevoked. There is no fail-closed policy for that case. When a CRL is returned but `ValidateCrl` fails, it returns 0 and the handshake fails ([ssl_transport_security.cc L1803-L1828](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/ssl_transport_security.cc#L1803-L1828)).
  - Java: no gRFC A69 CRL provider support.
  - Go: `checkCert` returns `RevocationUndetermined` whenever `fetchCRL` fails. That covers both "no CRL found for certificate's issuer" and a `verifyCRL` failure (issuer/key-ID mismatch, missing `cRLSign` when `KeyUsage` is present, bad signature). `checkChainRevocation` then allows the connection unless `DenyUndetermined` is set ([crl.go L119-L142](https://github.com/grpc/grpc-go/blob/cbf30c4130/security/advancedtls/crl.go#L119-L142), [L169-L214](https://github.com/grpc/grpc-go/blob/cbf30c4130/security/advancedtls/crl.go#L169-L214), [L365-L387](https://github.com/grpc/grpc-go/blob/cbf30c4130/security/advancedtls/crl.go#L365-L387)).
- **Prior documentation:**
  - gRFC A69 pseudocode: "`revocationStatus = checkRevocation(crl, cert) // RevocationUndetermined for null CRL`". It does not say what an invalid CRL yields.
  - gRFC A69: "If a CRL is not found for an issuer this is fine - the verification code will return RevocationUndetermined per RFC5280, then the user will have a setting to fail-open or fail-closed indicating whether RevocationUndetermined should be treated as Unrevoked or Revoked respectively."
  - gRFC A69: "Users should use `RevocationUndertermined` combined with the FailOpen/FailClosed knob for decision making on uncertain CRLs."
- **Decision:** (a) a present CRL that fails validation makes the status `Revoked` (fail closed), and `Undetermined` is used only when no CRL is found; or (b) keep the current spec (`Undetermined`, subject to the application's policy).
- **Recommendation:** (a). An invalid CRL for an issuer that has a configured CRL more likely means tampering or misconfiguration than a missing CRL, and under the default fail-open policy, (b) silently skips revocation checking for that issuer. The current text follows Go, so (b) is also consistent. Bugs if (a): Go (high), invalid CRL treated as `Undetermined`. Bugs if (b): C++ (medium), invalid CRL fails the handshake regardless of the `Undetermined` policy.
- **Why this rank:** Security behavior. With the default policy, the same corrupted CRL fails the handshake in C++ and lets it succeed in Go.

### CALL_CREDS-4. Token-fetching credentials: a fetch that returns an already-expired token (language divergence)

The spec doesn't cover a successful fetch that returns a token whose effective expiration (`exp − 30 s`) has already passed. Under the current pseudocode, the token is cached and backoff is reset, so every later attempt starts a new fetch with no backoff. C++ sends the expired token on the queued attempts, and Go fails them with `UNAVAILABLE`.

- **Where:** [6.3.3.2 Token Cache](06-security/03-call-credentials.md#32-token-cache) in `06-security/03-call-credentials.md`
- **Current spec:** "A token is *valid* while now < effective expiration." "If `exp` cannot be read (the token is malformed), the fetch counts as a failure with status `UNAUTHENTICATED`, and the cache is not updated." The algorithm's `on fetch completion` treats any "success with readable exp" as success: it caches the token, resets backoff, and completes every queued attempt with the token. "A successful fetch resets the backoff state."
- **Findings:**
  - C++: `TokenFetchComplete` caches any successful token, attaches it to every queued call, and drops the `FetchState` (and with it the backoff state). `GetRequestMetadata` then sees an expired token and starts a new fetch immediately, so each attempt fetches once and gets the expired token ([token_fetcher_credentials.cc L170-L186](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/credentials/call/token_fetcher/token_fetcher_credentials.cc#L170-L186), [L245-L262](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/credentials/call/token_fetcher/token_fetcher_credentials.cc#L245-L262)).
  - Java: the GCP authentication filter uses google-auth `IdTokenCredentials` over `ComputeEngineCredentials`, not a gRPC implementation of this algorithm ([GcpAuthenticationFilter.java L204-L212](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/GcpAuthenticationFilter.java#L204-L212)). Behavior with an expired token was not verified.
  - Go: `updateStateLocked` caches the token and resets `retryAttempt`/`nextRetryTime`. Waiters find no valid token and fail with `UNAVAILABLE` ("credentials: fetched token is expired"). The next attempt fetches again with no backoff ([gcp_service_account_identity_credentials.go L144-L152](https://github.com/grpc/grpc-go/blob/cbf30c4130/credentials/google/gcp_service_account_identity_credentials.go#L144-L152), [L233-L249](https://github.com/grpc/grpc-go/blob/cbf30c4130/credentials/google/gcp_service_account_identity_credentials.go#L233-L249)).
- **Prior documentation:**
  - gRFC A83: "If the `exp` field cannot be extracted (i.e., the JWT token is invalid), all queued data plane RPCs will be failed with status `UNAUTHENTICATED`. Otherwise, the cache is updated, and the returned token is added to all queued data plane RPCs, which may then continue." Read literally, this supports C++: an expired token is still added to the queued RPCs.
  - gRFC A83: "If the HTTP request does not result in the cache being updated (i.e., if the HTTP request fails or if it returns an invalid JWT token), backoff must be applied before the next attempt may be started." Backoff is tied to a failed cache update, so an expired-but-readable token resets backoff.
- **Decision:** (a) a fetched token whose effective expiration has passed counts as a fetch failure with `UNAUTHENTICATED`: the cache is not updated, the queued attempts fail, and backoff applies; (b) the same as (a) but with `UNAVAILABLE` (Go's code), on the theory that the token issuer's clock is skewed; (c) keep the A83 behavior (cache it and send it to the queued attempts) and state it explicitly.
- **Recommendation:** (a). Sending a token that the server will reject only moves the failure to the server. Without backoff, a skewed metadata server gets one request per RPC attempt. `UNAUTHENTICATED` matches the malformed-`exp` case. Bugs under (a): C++ (low), expired token cached and sent with no backoff. Go (low), wrong status and no backoff. Under (c): Go (low), queued attempts fail instead of getting the token.
- **Why this rank:** Rare (needs a broken or skewed token source), but no implementation applies backoff in that case, so the token endpoint gets one request per attempt.

### AUTHZ-20. Patterns with multiple or interior `*` in gRPC Authorization Policy (language divergence)

No implementation rejects a pattern with more than one `*` (such as `**` or `*abc*`). C++ and Java turn it into a suffix match, and Go turns it into a prefix match. A pattern with only an interior `*` (`a*b`) is an exact match on the literal string in all three.

- **Where:** [6.4.2.2 Pattern Syntax](06-security/04-authorization.md#22-pattern-syntax) in `06-security/04-authorization.md`
- **Current spec:** The table defines `*` (presence), `*abc` (suffix), `abc*` (prefix), and `abc` (exact). It doesn't say whether other placements of `*` are invalid or how they are interpreted.
- **Findings:**
  - C++: `GetMatcherType` checks `StartsWith(value, "*")` before `EndsWith(value, "*")`, so `*abc*` becomes suffix `abc*`, `**` becomes suffix `*`, and `a*b` becomes exact `a*b` ([rbac_translator.cc L49-L64](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/lib/security/authorization/rbac_translator.cc#L49-L64)).
  - Java: `getStringMatcher` checks `startsWith("*")` before `endsWith("*")` and behaves the same as C++ ([AuthorizationPolicyTranslator.java L47-L57](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/authz/src/main/java/io/grpc/authz/AuthorizationPolicyTranslator.java#L47-L57)).
  - Go: `getStringMatcher` and `getHeaderMatcher` check `HasSuffix(value, "*")` before `HasPrefix(value, "*")`, so `*abc*` becomes prefix `*abc`, `**` becomes prefix `*`, and `a*b` becomes exact `a*b` ([rbac_translator.go L113-L163](https://github.com/grpc/grpc-go/blob/cbf30c4130/authz/rbac_translator.go#L113-L163)).
- **Prior documentation:**
  - gRFC A43 schema (`principals`, and the same text for `paths` and header `values`): "The field supports Exact, Prefix, Suffix and Presence matches." / "- Exact match: \"abc\" will match on value \"abc\"." / "- Prefix match: \"abc*\" will match on value \"abc\" and \"abcd\"." / "- Suffix match: \"*abc\" will match on value \"abc\" and \"xabc\"." / "- Presence match: \"*\" will match when the value is not empty." Other placements of `*` are not covered.
- **Decision:** (a) a pattern that still contains `*` after removing a single leading or trailing `*` (other than `*` itself) makes the policy invalid; (b) specify the C++/Java interpretation (leading `*` first, remaining `*` literal) and file a Go bug; or (c) treat `*` as a wildcard only in the four forms in the table and as a literal elsewhere, which leaves `*abc*` and `**` to (a) or (b).
- **Recommendation:** (a). A user who writes `"*admin*"` probably expects a substring match and silently gets a suffix match (C++/Java) or a prefix match (Go) on a literal `*`. Rejecting the policy surfaces the mistake. Bugs if (a): C++, Java, and Go (low), patterns with extra `*` accepted. Bugs if (b): Go (low).
- **Why this rank:** Authorization matching differs across languages for the same policy (`*abc*` matches `xabc*` in C++/Java but `*abcx` in Go). Such patterns are unusual.

### AUTHZ-6. C++ aborts on duplicate audit logger factory registration (language divergence)

The spec says the last registration under a name wins. C++ aborts the process instead.

- **Where:** [6.4.3.5 Logger Registry and Plugin Contract](06-security/04-authorization.md#35-logger-registry-and-plugin-contract) in `06-security/04-authorization.md`
- **Current spec:** "If two factories are registered under the same name, the last one wins."
- **Findings:**
  - C++: `GRPC_CHECK(registry->logger_factories_map_.emplace(name, std::move(factory)).second)`. A duplicate, including an application factory named `stdout_logger` (which is built in), crashes the process ([audit_logging.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/lib/security/authorization/audit_logging.cc#L50-L57)).
  - Java: no audit logging.
  - Go: `registry.builders[b.Name()] = b`, so the last registration wins ([audit_logger.go](https://github.com/grpc/grpc-go/blob/v1.82.0/authz/audit/audit_logger.go#L46-L50)).
- **Prior documentation:**
  - gRFC A59, Go API: "If multiple builders are registered with the same name, the one registered last will take effect." The C++ API says only: "Registers an audit logger factory. This should only be called during initialization." It gives no duplicate rule.
- **Decision:** (a) last wins (Go, A59 Go API), (b) a duplicate is an error, reported in an implementation-defined way (C++ crash allowed), (c) implementation-defined.
- **Recommendation:** (c), with "SHOULD NOT register two factories under the same name". Registration happens at init and is under the application's control. Under (c), no bugs. If the owner prefers (a), record a low C++ bug.
- **Why this rank:** Init-time programming error only.

### ALTS-3. Validation of the handshaker service's response (language divergence)

The languages check different parts of the `HandshakerResp` and `HandshakerResult`. C++ checks the most fields but accepts any non-empty `record_protocol`; Go checks the record protocol but not the key length; Java checks only the key length.

- **Where:** [6.5.3.3 Handshake Result](06-security/05-alts.md#33-handshake-result) in `06-security/05-alts.md`
- **Current spec:** "`record_protocol` | MUST be `ALTSRP_GCM_AES128_REKEY` (the only protocol offered); otherwise the handshake fails." "`key_data` | MUST be at least 44 bytes; otherwise the handshake fails." It says nothing about a response with no `status` or a result with empty identities or protocols.
- **Findings:**
  - C++: a `HandshakerResp` with no `status` fails with `TSI_DATA_CORRUPTED` ([alts_handshaker_client.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/alts/handshaker/alts_handshaker_client.cc#L257-L264)). A result fails if it has no peer identity, an empty peer service account, `key_data` shorter than 44 bytes, no `peer_rpc_versions`, an empty application or record protocol, or no local identity ([alts_tsi_handshaker.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/alts/handshaker/alts_tsi_handshaker.cc#L298-L346)). The `record_protocol` value is not checked: any non-empty name is accepted, and `ALTSRP_GMAC_128` switches the connection to integrity-only protection ([L161](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/alts/handshaker/alts_tsi_handshaker.cc#L161), [L223-L230](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/tsi/alts/handshaker/alts_tsi_handshaker.cc#L223-L230)).
  - Java: a missing `status` reads as the default (code 0, OK) ([AltsHandshakerClient.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/alts/src/main/java/io/grpc/alts/internal/AltsHandshakerClient.java#L152-L164)). The only result check is `key_data` of at least 44 bytes ([L137-L147](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/alts/src/main/java/io/grpc/alts/internal/AltsHandshakerClient.java#L137-L147), [AltsTsiHandshaker.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/alts/src/main/java/io/grpc/alts/internal/AltsTsiHandshaker.java#L190-L205)). `record_protocol` is never read for validation; the frame protector always uses the rekeying AES-GCM crypter.
  - Go: a missing `status` is treated as OK. A `record_protocol` other than `ALTSRP_GCM_AES128_REKEY` fails ("unknown resulted record protocol"). `key_data` is sliced to 44 bytes with no length check, so a shorter key panics ([handshaker.go](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/credentials/alts/internal/handshaker/handshaker.go#L263-L301), [L52-L54](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/credentials/alts/internal/handshaker/handshaker.go#L52-L54)).
- **Prior documentation:**
  - grpc-proto `grpc/gcp/handshaker.proto`, `HandshakerResult.key_data`: "Cryptographic key data. The key data may be more than the key length required for the record protocol, thus the client of the handshaker service needs to truncate the key data into the right key length."
  - `HandshakerResult.record_protocol`: "The record protocol negotiated for this connection." `HandshakerResp.status`: "Status of the handshaker."
- **Decision:** (a) keep the spec as is (record protocol and key length only). (b) Keep (a), and also let implementations reject other malformed responses (no `status`, empty peer service account, missing `peer_rpc_versions`, and so on); a missing `status` MAY be treated as OK. (c) Require the full C++ set of checks.
- **Recommendation:** (b). The handshaker service is trusted, so the checks guard against bugs rather than attacks, but the two rules the spec already has matter: gRPC offered only `ALTSRP_GCM_AES128_REKEY`, and accepting another protocol (C++ silently drops to integrity-only for `ALTSRP_GMAC_128`) or a short key (Go panics) is unsafe. Bugs: C++ (low): `record_protocol` other than `ALTSRP_GCM_AES128_REKEY` accepted, and `ALTSRP_GMAC_128` gives integrity-only protection. Java (low): `record_protocol` never checked. Go (low): `key_data` shorter than 44 bytes panics instead of failing the handshake.
- **Why this rank:** Only a buggy handshaker service sends such a response, but the C++ and Go outcomes (weaker protection, a crash) are worse than a failed handshake.

### ORCA_SVC-21. Server-configured minimum reporting interval: values below 30 s and non-positive values in `OpenRcaService` (language divergence)

C++ and Java honor a configured minimum reporting interval below 30 s, whereas Go raises any value below 30 s to 30 s. For a zero or negative value, Java and Go use 30 s, whereas C++ uses the value as given, which yields a zero reporting interval when the client's `report_interval` is unset.

- **Where:** [7.3.4.2 Server Behavior](07-services/03-orca.md#42-server-behavior) in `07-services/03-orca.md`
- **Current spec:** "It has one setting, the **minimum reporting interval**, which defaults to **30 seconds**." The effective interval is `max(request.report_interval, min_report_interval)`, with an unset `report_interval` treated as 0. The spec says nothing about a floor or about non-positive settings.
- **Findings:**
  - C++: `OrcaService::Options::min_report_duration` defaults to `absl::Seconds(30)` and is stored as given, so positive values below 30 s are honored. `ReactorHook` computes `report_interval_ = std::max(report_interval, min_interval)`. With a zero or negative minimum and an unset or zero client `report_interval`, the interval is 0 and the report timer re-arms immediately ([orca_service.h L47-L55](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/include/grpcpp/ext/orca_service.h#L47-L55), [orca_service.cc L90-L99](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/cpp/server/orca/orca_service.cc#L90-L99)).
  - Java: `OrcaServiceImpl.createService(..., minInterval, timeUnit)` honors any positive value (including values below 30 s) and replaces a non-positive value with the 30 s default (`minInterval > 0 ? timeUnit.toNanos(minInterval) : DEFAULT_MIN_REPORT_INTERVAL_NANOS`) ([OrcaServiceImpl.java L61-L88](https://github.com/grpc/grpc-java/blob/ed3bf6b76b/xds/src/main/java/io/grpc/xds/orca/OrcaServiceImpl.java#L61-L88)).
  - Go: `NewService` replaces any `ServiceOptions.MinReportingInterval` below 30 s (including zero, negative, and values like `5s`) with 30 s, unless the unexported, test-only `allowAnyMinReportingInterval` is set ([service.go L42-L45](https://github.com/grpc/grpc-go/blob/cbf30c4130/orca/service.go#L42-L45), [service.go L94-L110](https://github.com/grpc/grpc-go/blob/cbf30c4130/orca/service.go#L94-L110)).
- **Prior documentation:**
  - gRFC A51 ("Out of Band Metrics Reporting" › "The Server API"): "A minimum reporting interval (30s by default) can be configured when creating the service. The minimum report interval is the lower bound of the OOB metrics report period. It means, if the `report_interval` from the client OOB request message is less than the service configured minimum interval then it is treated as the service minimum interval."
- **Decision:** (a) honor any positive configured minimum (including values below 30 s), and use the 30 s default when the configured value is zero or negative (Java); or (b) allow implementations to enforce a 30 s floor on the configured minimum (Go), still with non-positive values using the default.
- **Recommendation:** (a). `weighted_round_robin` requests a 10 s OOB period by default (`oobReportingPeriod`), and a 30 s floor on the server makes that period impossible to honor. A51 calls the setting configurable and gives 30 s only as the default. Bugs under (a): Go (low): `MinReportingInterval` below 30 s is raised to 30 s; C++ (low): a zero or negative `min_report_duration` is not replaced by the default, which leads to a zero reporting interval.
- **Why this rank:** Determines whether servers can support `weighted_round_robin`'s default OOB reporting period. The non-positive case is a configuration error.

### CHANNELZ-1. Channel trace memory bound is not configurable everywhere, and Java disables trace by default (language divergence)

The spec requires a way to control the trace memory bound through the channel and server APIs. Only C++ does this. Java's control is per channel only and defaults to 0, which turns channel trace off. Go has no public control.

- **Where:** [8.6.7.2 Memory Bound](08-observability/06-channelz.md#72-memory-bound) in `08-observability/06-channelz.md`
- **Current spec:** "Implementations MUST provide a way to control the bound." API Requirements: "The channel and server APIs MUST provide a way to configure the channel trace memory bound." Section 7.3 lists events that MUST be logged.
- **Findings:**
  - C++: channel arg `GRPC_ARG_MAX_CHANNEL_TRACE_EVENT_MEMORY_PER_NODE` on channels, subchannels, and servers, default 4 KiB ([channelz.h](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/channelz/channelz.h#L71-L77), [channel_create.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/lib/surface/channel_create.cc#L76-L80), [server.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/server/server.cc#L1066-L1069)).
  - Java: `ManagedChannelBuilder.maxTraceEvents(int)` only. The builder field defaults to 0, and `ChannelTracer` keeps no events when `maxEvents` is not positive, so channel trace (including the required events) is off unless the application opts in ([ManagedChannelImplBuilder.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/ManagedChannelImplBuilder.java#L586-L588), [ChannelTracer.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/ChannelTracer.java#L63-L72)). Servers have no trace (`ServerStats` has no trace field) ([InternalChannelz.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/api/src/main/java/io/grpc/InternalChannelz.java#L292-L297)).
  - Go: fixed at 30 events per entity. The setter `SetMaxTraceEntry` is in `internal/channelz`, so applications cannot call it ([trace.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/channelz/trace.go#L31-L50)). Servers have no trace.
- **Prior documentation:**
  - gRFC A3, Memory Limitation: "Implementations MUST provide some control for limiting the amount of memory used for channel trace events, such as a max number of trace events per node or the max amount of memory used." The control is required, but A3 does not say it must be per channel or per server, or what the default is.
- **Decision:** (a) keep both MUSTs (C++ conforms; Java needs a server control only if it adds server trace, and a non-zero default; Go needs a public control), (b) relax the API requirement to "MUST provide some way (for example a global setting) to control the bound" and add "trace MUST be enabled by default", or (c) relax both and allow trace to be off by default.
- **Recommendation:** (b). A3 requires only "some control", and a global setting is enough. Trace that is off by default defeats the 7.3 required events. Bugs: Java (medium): channel trace disabled by default (`maxTraceEvents` = 0). Go (low): no public way to change the trace bound.
- **Why this rank:** With Java's default, channelz shows no trace events for Java channels, which removes most of channelz's debugging value.

### XDS_BOOTSTRAP-5. When certificate_providers entries are validated (language divergence)

The three languages validate bootstrap `certificate_providers` entries at different times and for different things.

- **Where:** [9.2.4.4 Certificate Provider Instances](09-xds/02-bootstrap.md#44-certificate-provider-instances) in `09-xds/02-bootstrap.md`
- **Current spec:** `plugin_name` "MUST be a plugin that gRPC supports, or the bootstrap is invalid". `config` is not required, defaults to `{}`, and "MUST be valid for the plugin, or the bootstrap is invalid".
- **Findings:**
  - C++: conforms. An unknown plugin name or an invalid config makes the bootstrap invalid, and a missing config is treated as `{}` ([certificate_provider_store.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/xds/grpc/certificate_provider_store.cc#L44-L75))
  - Java: requires `config` to be present (`checkForNull`), but checks neither the plugin name nor the config at bootstrap time ([BootstrapperImpl.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/client/BootstrapperImpl.java#L181-L196)). An unknown plugin fails only when a resource uses the instance ([CertificateProviderStore.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/internal/security/certprovider/CertificateProviderStore.java#L129-L131))
  - Go: skips entries with an unknown plugin name and rejects the bootstrap for an invalid config ([bootstrap.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/xds/bootstrap/bootstrap.go#L608-L624))
- **Prior documentation:**
  - gRFC A29: the value "is a JSON object having exactly 2 fields: `plugin_name` … and `config`". It says nothing about when validation happens.
  - doc/grpc_xds_bootstrap_format.md: "The \"config\" field is optional; it may be missing if the credential type does not require config parameters." So Java requiring `config` is wrong.
- **Decision:** (a) keep the spec: validate at bootstrap time and reject unknown plugins (C++), or (b) ignore unknown plugins at bootstrap time (Go), so that a resource naming that instance is then NACKed, or (c) implementation-defined.
- **Recommendation:** (a). It matches the spec's general rule that the bootstrap fails with every validation error found, and it surfaces misconfiguration at start-up instead of as a NACK later. Bugs: Java (low): certificate provider plugin name and config are not validated at bootstrap time, and a missing `config` is rejected. Go (low): an unknown certificate provider `plugin_name` is ignored instead of rejected.
- **Why this rank:** Only affects misconfigured bootstraps. The failure shows up later or in a different form.

### XDS_CLIENT-7. Restarting the 15-second does-not-exist timer on ADS stream restart (language divergence)

When a new ADS stream starts and re-subscribes to watched resources, C++, Java, and Go diverge three ways on which uncached resources get the 15-second (or 30-second) does-not-exist timer again.

- **Where:** [9.3.7.4 Does-not-exist timer](09-xds/03-xds-client.md#74-does-not-exist-timer) in `09-xds/03-xds-client.md`
- **Current spec:** "**Stop**: when the resource, or a server-reported error for it, arrives on the stream, or when the stream ends. On a new stream, the timer starts again under the same rules if the entry still holds no cached resource."
- **Findings:**
  - C++: conforms. `MaybeStartTimer` starts the timer on the new stream whenever the entry has no cached resource (`!state.HasResource()`), including entries in `REQUESTED`, `DOES_NOT_EXIST`, `TIMEOUT`, uncached `NACKED`, and uncached `RECEIVED_ERROR`. When it fires again, watchers get another does-not-exist / timeout notification ([xds_client.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/xds/xds_client/xds_client.cc#L189-L227)).
  - Java: `startMissingResourceTimers` calls `restartTimer()` only when `!subscriber.hasResult()`, and `restartTimer` returns early if `data != null || absent`. `absent` is set for both `DOES_NOT_EXIST` and `TIMEOUT`, so the timer restarts for `REQUESTED` and uncached `NACKED` entries but not for `DOES_NOT_EXIST` or `TIMEOUT` ([XdsClientImpl.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/client/XdsClientImpl.java#L204-L216), [XdsClientImpl.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/client/XdsClientImpl.java#L774-L777)).
  - Go: the ADS stream keeps a per-resource watch state (`Started`, `Requested`, `Received`, `Timeout`). On stream failure, `onError` moves `Requested` entries back to `Started`. On the new stream, `sendExisting` calls `startWatchTimersLocked`, which starts timers only for `Started` entries. So only resources that have never had a response or a timeout get a new timer; resources that timed out, or that were received at any time (including NACKed or deleted ones with no cached value), do not ([ads_stream.go](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/xds/clients/xdsclient/ads_stream.go#L343-L375), [ads_stream.go](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/xds/clients/xdsclient/ads_stream.go#L578-L610), [ads_stream.go](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/xds/clients/xdsclient/ads_stream.go#L618-L638)).
- **Prior documentation:**
  - gRFC A57 covers when the timer starts on a new stream, not which resources get it: "XdsClient will start a new ADS stream and immediately send the subscription requests for the resources that it needs from this server, but because those requests will actually be queued in the xDS channel until the channel becomes connected, we don't want to start the timers for those resources until that happens."
  - gRFC A88: "by definition this timer will fire only when we do not have a version of the resource cached." A88's cache states (`DOES_NOT_EXIST`, `TIMEOUT`, `NACKED`, `RECEIVED_ERROR`) are distinct from `REQUESTED`, but A88 does not say which of them restart the timer on a new stream.
- **Decision:** (a) restart the timer for any watched resource with no cached value (C++, current spec), (b) restart it for entries with neither a cached value nor a does-not-exist/timeout result (Java), or (c) restart it only for resources that have not yet had any response or timeout (Go).
- **Recommendation:** (c), or allow either (a) or (c). Once a resource is in `DOES_NOT_EXIST`, `TIMEOUT`, `NACKED`, or `RECEIVED_ERROR` with no cached value, watchers already have an error, and firing the timer again after every reconnect adds nothing.
- **Why this rank:** Edge-case difference in repeated watcher notifications and CSDS status transitions after an ADS reconnect for a missing or invalid resource.

### XDS_ROUTING-11. `RetryPolicy.retry_on`: whitespace and case (language divergence)

C++ splits `retry_on` on `,` with no trimming and matches names case-sensitively. Java and Go trim whitespace and match case-insensitively, and Envoy trims but matches case-sensitively. So `"cancelled, unavailable"` gives C++ only `cancelled`.

- **Where:** [9.4.3.8 Retry Policy](09-xds/04-resources/03-route-configuration.md#8-retry-policy) in `09-xds/04-resources/03-route-configuration.md`
- **Current spec:** "`retry_on` | Comma-separated list of conditions. Only `cancelled`, `deadline-exceeded`, `internal`, `resource-exhausted`, and `unavailable` are recognized (mapping to the status codes of the same name). All other conditions are ignored."
- **Findings:**
  - C++: `absl::StrSplit(retry_on, ',')` and exact string comparisons. A token with surrounding spaces or a different case is logged (with tracing on) and ignored ([xds_route_config_parser.cc L354-L373](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/xds/grpc/xds_route_config_parser.cc#L354-L373)).
  - Java: `Splitter.on(',').omitEmptyStrings().trimResults()`, then `Status.Code.valueOf(retryOn.toUpperCase(Locale.US).replace('-', '_'))`, keeping only the five supported codes. Matching is case-insensitive, and the underscore spellings (for example `deadline_exceeded`) are also accepted ([XdsRouteConfigureResource.java L560-L576](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/XdsRouteConfigureResource.java#L560-L576)).
  - Go: `strings.Split(..., ",")`, then `strings.TrimSpace(strings.ToLower(s))` against the five names ([unmarshal_rds.go L178-L191](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/internal/xds/xdsclient/xdsresource/unmarshal_rds.go#L178-L191)).
  - Envoy: `StringUtil::splitToken(config, ",", false, true)` (drop empty tokens, trim whitespace), then exact comparisons ([retry_state_impl.cc L215-L235](https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/source/common/router/retry_state_impl.cc#L215-L235)).
- **Prior documentation:**
  - gRFC A44: "When converting `retry_on` value to `retryableStatusCodes`, the gRPC xDS client will only convert conditions that are documented in [x-envoy-retry-grpc-on](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter#x-envoy-retry-grpc-on), that is, \"cancelled\", \"deadline-exceeded\", \"internal\", \"resource-exhausted\" and \"unavailable\", and will ignore any other conditions." A44 lists lowercase names and says nothing about whitespace or case.
- **Decision:** (a) trim whitespace around each condition and match case-sensitively (Envoy); (b) trim whitespace and match case-insensitively (Java, Go); or (c) no trimming, case-sensitive (C++).
- **Recommendation:** (b). Every value Envoy accepts also works under (b), and only one implementation needs a change. A condition that gRPC matches more loosely than Envoy can only add retries the operator clearly meant to configure. Bugs under (b): C++ (low): `retry_on` conditions with surrounding whitespace or non-lowercase names ignored. Optionally, Java (low): accepts underscore spellings such as `deadline_exceeded`. Under (a), Java and Go get a low bug for case-insensitive matching.
- **Why this rank:** A control plane that writes `"a, b"` silently loses retries on C++ only. Most control planes write the names without spaces.

### XDS_DEPMGR-5. When the XdsDependencyManager delivers a config (language divergence)

Languages differ on which pending resources hold back a new `XdsConfig`. Go doesn't wait for dynamically subscribed clusters, and Java can wait on clusters that are no longer needed.

- **Where:** [9.5.2.7 When a config is delivered](09-xds/05-client.md#27-when-a-config-is-delivered) in `09-xds/05-client.md`
- **Current spec:** A config is delivered if and only if a valid Listener and virtual host exist, and every cluster reachable from the root set (route clusters plus dynamic subscriptions) has its CDS result and endpoint data or error.
- **Findings:**
  - C++: conforms. It walks every root, including subscriptions, and returns no config if anything is missing ([xds_dependency_manager.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/resolver/xds/xds_dependency_manager.cc#L892-L961)).
  - Go: `haveAllResources` becomes false only for clusters with `staticRefCount > 0`. A pending dynamic cluster (and everything under it) is left out of the config, and the config is delivered anyway ([xds_dependency_manager.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/xds/xdsdepmgr/xds_dependency_manager.go#L234-L253)).
  - Java: waits until no watcher it holds has a missing result ([XdsDependencyManager.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/XdsDependencyManager.java#L196-L206)). Unneeded watchers are closed only after a config is built ([L219-L227](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/XdsDependencyManager.java#L219-L227)). So if a route update removes a cluster whose CDS response never arrived, all further updates are blocked until that resource arrives or its does-not-exist timer fires. I found this by reading the code; I didn't test it.
- **Prior documentation:**
  - gRFC A74, "Changes in cds LB policy": "when a cds LB policy obtains a dynamic subscription to a cluster, there may be subsequent updates from the xds resolver that do not yet include the newly subscribed-to cluster. Therefore, the cds policy will need to ignore updates in which the XdsConfig does not contain the cluster." This expects updates that don't include a just-subscribed cluster, so Go's approach is arguably allowed.
  - gRFC A74: "Only once it has all necessary resources will it return a new configuration to the xds resolver."
- **Decision:** (a) keep the strict rule (C++), (b) let a config be delivered without dynamically subscribed clusters that are still pending, which then have no entry (Go), (c) leave it implementation-defined. In all cases, state that resources no longer needed MUST NOT hold back delivery.
- **Recommendation:** (b). Bugs: under (b), C++ (low): pending dynamic subscriptions block all config delivery. Under any option, Java (medium): watchers for clusters no longer needed can block config delivery.
- **Why this rank:** Affects how fast updates arrive in edge cases. Java's case can delay every update by up to the does-not-exist timeout.

### XDS_FILTERS-1. HttpFilter / FilterConfig `disabled` fields (language divergence)

`HttpFilter.disabled` and `FilterConfig.disabled` let a filter be turned off by default and re-enabled per route, but no merged gRFC specifies them.

- **Where:** [9.7.2.1 Extracting the Filter Type](09-xds/07-http-filters.md#21-extracting-the-filter-type) in `09-xds/07-http-filters.md`
- **Current spec:** Does not mention the fields, so they are ignored.
- **Findings:**

  - C++: always honored, with precedence ClusterWeight > Route > VirtualHost > HCM (`xds_routing.cc` `IsFilterDisabled`) ([xds_routing.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/xds/grpc/xds_routing.cc#L280-L314)).

- **Prior documentation:**
  - gRFC A39 (xDS HTTP filters) lists the `HttpFilter` fields gRPC uses (`name`, `typed_config`, `is_optional`), and for `FilterConfig` says "gRPC will look inside that type's [`config`] field ... In addition, gRPC will look at the [`is_optional`] field". It never mentions `disabled`, which supports option (a).

Envoy `route_components.proto`, `FilterConfig.disabled`: "If true, the filter is disabled in the route or virtual host and the ``config`` field is ignored."

### XDS_GCP_AUTHN-2. GCP authentication filter: combine with or replace application per-call credentials (language divergence)

When the GCP authentication filter attaches its audience-specific call credentials to an RPC that already has per-call credentials set by the application, C++ and Go replace the application's credentials, while Java combines both. The spec and gRFC A83 only say "attach".

- **Where:** [10.4.3 Per-RPC Behavior](10-vendor-specific/04-gcp-authentication-filter.md#3-per-rpc-behavior) in `10-vendor-specific/04-gcp-authentication-filter.md`
- **Current spec:** Step 5: "obtain from the instance's cache … the GCP service-account identity call credentials for the audience `url`, creating and inserting them if absent, and attach them to the RPC." [Security Model: Call Credentials](06-security/01-security-model.md#3-call-credentials) says channel-level and per-call call credentials both apply, but says nothing about a second set of per-call credentials added by a filter.
- **Findings:**
  - C++: if the call already has a `grpc_client_security_context`, the filter overwrites its `creds` (`security_ctx->creds = std::move(creds)`), so per-call credentials set with `ClientContext::set_credentials` are silently dropped. Channel-level call credentials are not affected ([gcp_authentication_filter.cc L111-L123](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/ext/filters/gcp_authentication/gcp_authentication_filter.cc#L111-L123)).
  - Java: if `callOptions.getCredentials()` is non-null, the filter installs `new CompositeCallCredentials(existingCallCredentials, newCallCredentials)`, so both sets of metadata are sent ([GcpAuthenticationFilter.java L189-L197](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/GcpAuthenticationFilter.java#L189-L197)).
  - Go: the interceptor appends `grpc.PerRPCCredentials(creds)` after the application's call options ([gcp_authn_filter.go L204-L212](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/internal/xds/httpfilter/gcpauthn/gcp_authn_filter.go#L204-L212)). `callInfo` holds a single per-call credential, and `PerRPCCredsCallOption.before` assigns it (`c.creds = o.Creds`), so the filter's option, applied last, replaces the application's ([rpc_util.go L497-L500](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/rpc_util.go#L497-L500), [stream.go L401-L405](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/stream.go#L401-L405)). The source report said Go combines them; that is not what the code does.
  - Envoy: Envoy has no call credentials. The filter writes the token with `setCopy`, which overwrites the target header (`authorization` by default) and leaves other headers alone. `token_header.preserve_existing` makes it keep an existing header instead ([gcp_authn_filter.cc L131-L136](https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/source/extensions/filters/http/gcp_authn/gcp_authn_filter.cc#L131-L136), [gcp_authn_filter.cc L292](https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/source/extensions/filters/http/gcp_authn/gcp_authn_filter.cc#L292), [gcp_authn.proto L170-L175](https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/api/envoy/extensions/filters/http/gcp_authn/v3/gcp_authn.proto#L170-L175)).
- **Prior documentation:**
  - gRFC A83, filter behavior: "It will then attach that GcpServiceAccountIdentityCallCredentials instance to the RPC." and "Instead, it must add the call credential to the RPC, and the call credential will do the work of adding the token to the RPC later". "Attach" and "add" don't say whether existing per-call credentials are kept.

- **Recommendation:** (a). The application's per-call credentials may carry unrelated metadata (for example an API key or a different header), and dropping them silently is surprising. It also fits the Security Model rule that call credentials from different sources all apply. If both produce `authorization`, both values are sent, which is the same result as channel-level plus per-call credentials today. Bugs under (a): C++ (medium) and Go (medium): GCP authentication filter replaces application per-call credentials instead of combining them.

### RING_HASH-22. Endpoints that share a `hash_key`: failover and stable choice (judgment)

When several endpoints share a `hash_key`, Go makes only one of them reachable: it is picked even when it is in TRANSIENT_FAILURE, and which one it is can change on every picker rebuild. C++ picks one deterministically and fails over to the others.

- **Where:** [`ring_hash` LB Policy: 2.1 Other Inputs](04-client-channel/lb-policies/ring_hash.md#21-other-inputs) in `04-client-channel/lb-policies/ring_hash.md`
- **Current spec:** `hash_key` row: "If several endpoints share a `hash_key`, the endpoint chosen among them for a given ring position is unspecified." Endpoints are identified by their address sets (3.3), so such endpoints are distinct, each with its own child. Ring Construction hashes `key + "_" + count`, so the endpoints get identical ring hashes.
- **Findings:**
  - C++: the ring is sorted by hash only (`std::sort`, deterministic for a given input order). The binary search lands on the first entry of a run of equal hashes, so for each position one endpoint among the duplicates gets the traffic. The others' entries come right after it, so the TRANSIENT_FAILURE walk reaches them ([ring_hash.cc L305-L399](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/load_balancing/ring_hash/ring_hash.cc#L305-L399), [L508-L511](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/load_balancing/ring_hash/ring_hash.cc#L508-L511)).
  - Java: doesn't support `hash_key` (existing Java bug "ring_hash does not support the `hash_key` endpoint attribute"). It always hashes the first address, so the case doesn't arise.
  - Go: ring entries record only `hashKey`. `newPickerLocked` copies endpoint states into `map[string]endpointState` keyed by `hashKey`, iterating a `resolver.EndpointMap` (backed by a Go map) in random order. The last endpoint written wins, and `picker.endpointState` resolves every entry for that key to it. The losing endpoints are never picked. When the winner is in TRANSIENT_FAILURE, the walk skips every entry for the key, and the others are not tried. The winner can change on each rebuild, which happens on every endpoint state change. Only the balancer's proactive-connection loop, which sorts all endpoint states by `hashKey`, can still connect a losing endpoint ([ringhash.go L264-L270](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/ringhash.go#L264-L270), [ringhash.go L322-L341](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/ringhash.go#L322-L341), [picker.go L41](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/picker.go#L41), [picker.go L80-L91](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/picker.go#L80-L91), [picker.go L122-L124](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/picker.go#L122-L124), [ring.go L104-L115](https://github.com/grpc/grpc-go/blob/cbf30c41309983ce66c6a81abe569a75fd2b9dcd/balancer/ringhash/ring.go#L104-L115)).
- **Prior documentation:**
  - gRFC A76 ("Improvements to the Ring Hash LB Policy"): "If multiple endpoints have the same `hash_key`, then which endpoint is chosen is unspecified, and the implementation is free to choose any of the endpoints with a matching `hash_key`." This allows Go's choice for a pick, but doesn't address failover or stability.
- **Decision:** (a) keep "unspecified" as is (gRFC A76 explicitly gives implementations freedom); (b) keep the choice unspecified, but add that the choice SHOULD be stable across picker rebuilds while the endpoint list doesn't change, and that every endpoint that shares the key MUST stay reachable through the TRANSIENT_FAILURE walk (matches C++; Go bug); (c) only (b)'s stability SHOULD.
- **Recommendation:** (b). Ring hash exists for affinity, and a choice that changes whenever any endpoint changes state breaks affinity for every request on that key. Leaving some endpoints unreachable even as failover goes beyond what gRFC A76 meant by "free to choose". Record a low Go bug: ring_hash collapses endpoints that share a `hash_key`, so only one is ever picked and the choice changes on picker rebuilds.
- **Why this rank:** Needs a misconfigured or unusual EDS (duplicate `hash_key` values), but then affinity and failover both break silently.

### RING_HASH-21. `IDLE` deadlock when `ring_hash` is a child of `weighted_target` (judgment)

When `weighted_target` wraps `ring_hash` children that are all `IDLE`, `weighted_target`'s `IDLE` picker queues RPCs and asks its children to exit idle. But `ring_hash`'s `ExitIdle()` is a no-op, so the queued RPCs stay stuck while everything remains `IDLE`.

- **Where:** [`ring_hash` LB Policy: 3.4 ExitIdle](04-client-channel/lb-policies/ring_hash.md#34-exitidle) in `04-client-channel/lb-policies/ring_hash.md`
- **Also found at:** [`weighted_target` LB Policy: 4. Picker Implementation](04-client-channel/lb-policies/weighted_target.md#4-picker-implementation) in `04-client-channel/lb-policies/weighted_target.md`
- **Current spec:** `ring_hash` initially reports `IDLE`, and its `ExitIdle()` has "No effect: connections are started by picks … and by the proactive connection rule" (decided in `Item 70`, which confirmed that all three implementations make it a no-op). `weighted_target` aggregates all-`IDLE` children to `IDLE`, and its `IDLE` picker queues and "MUST also schedule a call to the policy's `ExitIdle()`, which is forwarded to all children" (`R29`). `06-load-balancing.md` §4 defines `ExitIdle()` as "Asks the policy to leave IDLE and begin connecting. A no-op for policies that do not use IDLE."
- **Findings:**

### SERVER-7. Forced shutdown: whether to reset streams before closing connections (judgment)

The working draft changed forced shutdown from "SHOULD signal the cancellation to clients (for example, with `RST_STREAM`)" to "MAY reset streams ... or close the connections directly", and no owner decision covers the change. The choice decides what clients see: Java resets each stream (clients see `CANCELLED`), while C++ and Go just close the connection (clients see `UNAVAILABLE`).

- **Where:** [5.1.1.4 Forced Shutdown](05-server/01-server.md#14-forced-shutdown) in `05-server/01-server.md`
- **Current spec:** "Every in-flight RPC is **cancelled**. ... The server MAY reset active streams (for example, with `RST_STREAM(CANCEL)`) before closing every connection, or close the connections directly." Text at HEAD: "The server SHOULD signal the cancellation to clients (for example, with `RST_STREAM`), and then closes every connection." Related text: the server transport model says clients see such calls "as `UNAVAILABLE` (or `CANCELLED` / a protocol-mapped status if the server reset the stream before closing)". The HTTP/2 server transport says "It MAY first send a final `GOAWAY` or reset the active streams". The `RST_STREAM` table says servers SHOULD use `CANCEL` "only when they must cancel a call and cannot send a complete response".
- **Findings:**
  - C++: `Shutdown(deadline)` calls `grpc_server_cancel_all_calls` when the deadline passes. That broadcasts `disconnect_with_error`, and chttp2 sends a GOAWAY and calls `close_transport_locked`, which fails the streams locally and sends no per-stream `RST_STREAM` ([server_cc.cc L1277](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/cpp/server/server_cc.cc#L1277), [server.cc L1620-L1633](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/server/server.cc#L1620-L1633), [chttp2_transport.cc L2300-L2304](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2300-L2304)).
  - Java: `ServerImpl.shutdownNow` calls `NettyServerTransport.shutdownNow`, which writes a `ForcefulCloseCommand`. `forcefulClose` calls `Http2ConnectionHandler.close` (GOAWAY, then close) and then `resetStream(..., CANCEL)` for every active stream ([NettyServerTransport.java L188-L192](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/NettyServerTransport.java#L188-L192), [NettyServerHandler.java L898-L917](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/NettyServerHandler.java#L898-L917)).
  - Go: `Server.Stop` calls `st.Close` on each transport. `http2Server.Close` closes the `net.Conn` right away and cancels streams locally, with no GOAWAY and no `RST_STREAM` ([server.go L1705-L1709](https://github.com/grpc/grpc-go/blob/cbf30c4130/server.go#L1705-L1709), [server.go L1741-L1747](https://github.com/grpc/grpc-go/blob/cbf30c4130/server.go#L1741-L1747), [http2_server.go L1300-L1323](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/transport/http2_server.go#L1300-L1323)).
- **Prior documentation:**
  - Not covered by any prior documentation (searched: grpc-proposal gRFCs and `grpc/doc/*.md` for "shutdownNow", "forced shutdown", "forceful"; gRFC A9 covers only connection age and idle limits).
- **Decision:** (a) keep the relaxation (MAY reset streams or close directly), so clients may see `CANCELLED` or `UNAVAILABLE`; (b) restore the SHOULD for `RST_STREAM`, which makes C++ and Go deviate from a SHOULD; (c) say the server SHOULD NOT reset streams with `CANCEL` and just closes the connection (optionally after a GOAWAY), so clients consistently see `UNAVAILABLE`.
- **Recommendation:** (a). Closing the connection already tells the client that the calls ended. Two of three implementations don't send resets, and the transport docs already allow both. Under (a), no bugs. If the owner wants one client-visible status (`UNAVAILABLE` is retryable and matches the other forced-close cases), choose (c) and record a low Java bug.
- **Why this rank:** A normative relaxation the owner hasn't approved. It changes the status code clients see on forced shutdown, which matters for retry policies.

### XDS_RBAC-21. `RBAC.matcher` (`xds.type.matcher.v3.Matcher`) silently ignored and fails open (judgment)

`envoy.extensions.filters.http.rbac.v3.RBAC` defines an enforcing `matcher` field (`xds.type.matcher.v3.Matcher`, an alternative to `rules` that takes precedence over it), which the spec omits and C++, Java, and Go all silently ignore — allowing all RPCs when `matcher` is configured without `rules`, and enforcing `rules` instead of `matcher` when both are set.

  - `envoy/extensions/filters/http/rbac/v3/rbac.proto`: `rules`: "When both ``rules`` and ``matcher`` are configured, ``rules`` will be ignored." `matcher = 4`: "Match tree for evaluating RBAC actions on incoming requests. - **Decision:** (a) NACK `RBAC` when `matcher` is present (and list `shadow_matcher` and `track_per_rule_stats` as ignored alongside `shadow_rules`), filing security validation bugs against C++, Java, and Go; or (b) explicitly document `matcher`, `shadow_matcher`, and `track_per_rule_stats` as ignored until a gRFC adds matcher-tree RBAC support.

Ignoring `matcher` both weakens security (fail-open when `rules` is absent) and changes how the supported `rules` field is interpreted (Envoy ignores `rules` when `matcher` is set), which is exactly the case architecture §2.2 rule 3 requires to NACK. Bugs if (a): C++, Java, Go (medium): `RBAC.matcher` silently ignored.
- **Why this rank:** Security fail-open if a control plane deploys Envoy's matcher-based RBAC configuration to proxyless gRPC servers.

### SERVICE_CONFIG-9. When the method config timeout starts (language bug)

The spec says the method config `timeout` counts from when the application started the RPC. Go and Java start it when the config is applied, after any wait for the first resolver result.

- **Where:** [4.5.3.2 Applying the Method Config](04-client-channel/05-call-dispatch.md#32-applying-the-method-config) in `04-client-channel/05-call-dispatch.md`

- **Current spec:** `rpc.deadline = min(rpc.deadline, rpc.start_time + mc.timeout)`. "The timeout counts from the time the application started the RPC, not from the time the config was applied."
- **Findings:**
  - C++: the deadline is the call start time plus the timeout, in both client channel implementations ([client_channel.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/client_channel/client_channel.cc#L1485-L1491), [client_channel_filter.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/client_channel/client_channel_filter.cc#L185-L191))

  - Go: `context.WithTimeout(ctx, timeout)` in `newClientStreamWithParams`, after `waitForResolvedAddrs` and `SelectConfig` ([stream.go](https://github.com/grpc/grpc-go/blob/v1.82.0/stream.go#L240-L252), [stream.go](https://github.com/grpc/grpc-go/blob/v1.82.0/stream.go#L298-L302))

### HTTP2-3. Servers rejecting requests without `:authority` (language bug)

C++ servers fail a request that has neither `:authority` nor `Host` with grpc-status `UNKNOWN`. They also reject a request with a missing `te`.

A missing `te` is only logged ([NettyServerHandler.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/NettyServerHandler.java#L468-L480), [L531](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/NettyServerHandler.java#L531)).
  - Go: rejects a request with neither `:authority` nor `Host`: HTTP 400 with grpc-status `INTERNAL` ("no host or :authority header present") ([http2_server.go](https://github.com/grpc/grpc-go/blob/c2165f27d8bbc81e75aa14b82d23540882ac5f02/internal/transport/http2_server.go#L509-L528)). ### SERVICE_CONFIG-3. Invalid first service config: fall back to the default? (language bug)

gRFC A21 contradicts itself on what happens when the first config from the resolver is invalid, and Java also behaves differently when a previous valid config exists.

- **Where:** [4.4.3 Validation and Error Handling](04-client-channel/04-service-config.md#3-validation-and-error-handling) in `04-client-channel/04-service-config.md`
- **Current spec:** With a previous valid config, keep it. With none, report TRANSIENT_FAILURE and don't use the default config.
- **Findings:**
  - A21 step 5 says to treat the resolution as failed (TRANSIENT_FAILURE). Its "Service Config Channel Arguments" section says to fall back to the default config.
  - C++ keeps the saved config if there is one, otherwise reports TRANSIENT_FAILURE and ignores the default ([client_channel.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/client_channel/client_channel.cc#L1156-L1178)).
  - Go does the same ([clientconn.go](https://github.com/grpc/grpc-go/blob/c2165f27d8bbc81e75aa14b82d23540882ac5f02/clientconn.go#L851-L860)), despite what its `WithDefaultServiceConfig` godoc says ("The name resolver does not provide a service config or provides an invalid service config", [dialoptions.go](https://github.com/grpc/grpc-go/blob/c2165f27d8bbc81e75aa14b82d23540882ac5f02/dialoptions.go#L660-L667)).
  - Java falls back to the default whenever one is set, even replacing a previous valid config: the `defaultServiceConfig != null` branch is checked before `serviceConfigError` ([ManagedChannelImpl.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/ManagedChannelImpl.java#L1727-L1732)). Without a default, Java keeps the last config, or reports the error if no config was ever applied ([ManagedChannelImpl.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/core/src/main/java/io/grpc/internal/ManagedChannelImpl.java#L1733-L1747)), matching C++ and Go.
- **Prior documentation:**
  - gRFC A21 (service config error handling), step 5.2: "If the client has not previously selected a valid service config or no service config, for example a new client, then it treats the resolution attempt as having failed ... In other words, the channel will remain in state TRANSIENT_FAILURE until the resolver returns a valid response." Step 5.1: "If it previously had selected a valid service config or no service config, it should continue using that previous configuration". This matches option (a) and C++/Go.
  - gRFC A21, "Service Config Channel Arguments": "If a default service config is provided, the client should fallback on the default service config (in case of an invalid config with no valid service config received earlier). On the other hand, if there is no default service config provided as a channel argument, the client should fail to start and keep waiting for a valid service config." This is the conflicting text. Note that even this section limits fallback to "no valid service config received earlier", so nothing in A21 supports Java replacing a previous valid config.
  - gRFC A21, the second step 5 (numbering is duplicated): "If the resolver does not support service config resolution OR if no gRPC config is received OR if gRPC config is received but no service config is chosen ..., the client should use the default service config". Here the default applies only when *no* config is returned.
  - Pending PR grpc/grpc#38953 (client channel), "Channel Handling of Resolver Result" pseudocode: "if (channel.service_config != null) { // We have a valid service config from a previous resolver result, so keep using it. ... } else { // No previously returned valid config, so we fail. channel.SetConnectivityState(TRANSIENT_FAILURE);" The default is used only for `result.service_config.IsEmpty()`. Elsewhere it says: "The default config is used when the resolver does not return any service config." This exactly matches option (a).
  - Not covered by doc/service_config.md or grpc-proto.
- **Decision:** (a) no fallback (C++/Go), fixing A21's channel-arguments section and Go's godoc, or (b) fall back to the default when there is no previous valid config, treating C++ and Go as bugs.
- **Recommendation:** (a). It's what most implementations do, and an invalid config is a visible error rather than being hidden by a default the service owner never chose. File a bug against Java, especially for replacing a previous valid config. Update A21 and Go's godoc. Apply the same decision to item SERVICE_CONFIG-2.
- **Owner note:** Leave open.
- **Why this rank:** Java replacing a previous valid config with the default on a bad update changes channel behavior silently; C++/Go match the spec.

### TRANSPORT-5. MAX_CONNECTION_AGE_GRACE measured from the first GOAWAY in Go and C++ (language bug)

The spec, following A9, measures the grace period from the second GOAWAY. Go and C++ start it when the first GOAWAY is sent.

- **Where:** [5.2.2.6 Connection Management](05-server/02-transports/02-http2.md#6-connection-management) in `05-server/02-transports/02-http2.md`
- **Current spec:** Procedure: "`MAX_CONNECTION_AGE_GRACE` SHOULD be measured from the second GOAWAY of the graceful shutdown." Table: "The grace period for outstanding RPCs during an age-triggered graceful shutdown before the connection is forcibly closed."
- **Findings:**
  - C++: sends the GOAWAY op, then immediately sleeps for the grace period ([legacy_channel_idle_filter.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/ext/filters/channel_idle/legacy_channel_idle_filter.cc#L178-L216)).
  - Java: applies the grace time after the second GOAWAY in both Netty (`secondGoAwayAndClose`, [NettyServerHandler.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/netty/src/main/java/io/grpc/netty/NettyServerHandler.java#L1151-L1175)) and OkHttp (`triggerGracefulSecondGoaway`, [OkHttpServerTransport.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/okhttp/src/main/java/io/grpc/okhttp/OkHttpServerTransport.java#L308-L325)).
  - Go: `t.Drain("max_age")`, then `ageTimer.Reset(t.kp.MaxConnectionAgeGrace)` right away ([http2_server.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/transport/http2_server.go#L1229-L1231)).
- **Prior documentation:**
  - gRFC A9: "`MAX_CONNECTION_AGE_GRACE` is the maximum time the connection will be kept alive for outstanding RPCs to complete, ideally relative to the second GOAWAY of the graceful connection termination."
- **Decision:** (a) keep the SHOULD, file low bugs, and fix the table wording to match, (b) allow either starting point (MAY), since the difference is at most one PING round trip (bounded by the 5 s / 10 s / 20 s graceful-GOAWAY PING timeouts).
- **Recommendation:** (b) and fix the table. The difference is bounded and small, and "ideally" in A9 is weak. If (a) is chosen instead: Go (low) and C++ (low), grace measured from the first GOAWAY.
- **Why this rank:** Small timing difference, plus an internal wording inconsistency.

### SECURITY-1. Go checks channel-level call credentials' security level at channel creation or connection time (language bug)

For call credentials set on the channel, Go enforces the minimum security level by failing channel creation or the connection, not by failing the RPC with `UNAUTHENTICATED`.

- **Where:** [6.1.5.1 Call Credential Minimum Security Level](06-security/01-security-model.md#51-call-credential-minimum-security-level) in `06-security/01-security-model.md`
- **Current spec:** "If the connection's level is lower, the call credentials MUST NOT be invoked and their metadata MUST NOT be sent. The RPC fails with status `UNAUTHENTICATED` ..."
- **Findings:**
  - C++: channel and per-call credentials are combined and checked per RPC, returning `UnauthenticatedError("Established channel does not have a sufficient security level ...")` ([client_auth_filter.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/filter/auth/client_auth_filter.cc#L138-L157)).
  - Java: the check is inside the credentials. The built-in Google credentials fail the RPC with `UNAUTHENTICATED` ([GoogleAuthLibraryCallCredentials.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/auth/src/main/java/io/grpc/auth/GoogleAuthLibraryCallCredentials.java#L101-L105)). Custom credentials are already covered by an existing bug.
  - Go: with insecure transport credentials, `Dial`/`NewClient` fails with "the credentials require transport level security" ([clientconn.go](https://github.com/grpc/grpc-go/blob/v1.82.0/clientconn.go#L496-L501)). With other transport credentials below `PRIVACY_AND_INTEGRITY`, every connection fails right after the handshake as a temporary connection error ([http2_client.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/transport/http2_client.go#L299-L310)). RPCs then see `UNAVAILABLE`, or wait if wait-for-ready is set, and never `UNAUTHENTICATED`. Per-call credentials are checked per RPC with `UNAUTHENTICATED` ([http2_client.go](https://github.com/grpc/grpc-go/blob/v1.82.0/internal/transport/http2_client.go#L707-L711)).
- **Prior documentation:**
  - Not covered by any prior documentation (searched: A29, A54, A83, A97, doc/server_side_auth.md, grpc_security_constants.h comments).
- **Decision:** (a) Keep the spec: the check is per RPC, with `UNAUTHENTICATED`. (b) Also allow the channel to reject the configuration at creation time when it is statically known to be incompatible (insecure credentials plus channel-level credentials that need privacy). Keep the per-RPC `UNAUTHENTICATED` rule for connections whose level is only known after the handshake.
- **Recommendation:** (b). Failing fast at channel creation is safe and helpful. Failing every connection is not: it looks like a connectivity problem (`UNAVAILABLE`, TRANSIENT_FAILURE, backoff), and wait-for-ready RPCs hang. Bug: Go (low): channel-level call credentials with an insufficient connection security level fail the connection instead of the RPC with `UNAUTHENTICATED`.
- **Why this rank:** It is rare (it needs non-TLS, non-insecure transport credentials below privacy), but the error is misleading and RPCs can hang.

### ALTS-6. ALTS client authorization helper: case sensitivity and context API fields (language bug)

Go's server-side service-account check is case-insensitive, while C++ and Java compare exactly. Separately, Java's public ALTS context omits several fields the spec requires.

- **Where:** [6.5.8 API Requirements](06-security/05-alts.md#8-api-requirements) in `06-security/05-alts.md`
- **Current spec:** "The client and server call APIs MUST give access to the ALTS context of the connection an RPC used: at least the peer service account, the local service account, the security level, the application and record protocols, and the peer's RPC protocol versions." - **Prior documentation:**

### XDS_CLIENT-6. ADS stream reconnect delay after a stream that received a response closes (language bug)

When an ADS stream closes after having received at least one response, C++ and Java wait the initial backoff (~1 s) before starting the next stream, as the spec says. Go starts the next stream immediately.

- **Where:** [9.3.4.1 Stream lifecycle](09-xds/03-xds-client.md#41-stream-lifecycle) in `09-xds/03-xds-client.md`
- **Current spec:** "When the stream ends for any reason other than XdsClient shutdown, the XdsClient MUST start a new stream after a backoff delay. … The backoff state MUST be reset whenever a stream receives a response, so after a stream that received at least one response, the next attempt uses the initial backoff."
- **Findings:**
  - C++: conforms. `RetryableCall::OnCallFinishedLocked` resets the backoff if the call saw a response and always calls `StartRetryTimerLocked`, which waits `backoff_.NextAttemptDelay()` (the initial 1 s with jitter after a reset) ([xds_client.cc](https://github.com/grpc/grpc/blob/515aaa1743ec9a318e7e22d11a5bfaa835d5fa81/src/core/xds/xds_client/xds_client.cc#L641-L677)).
  - Java: conforms. `handleRpcStreamClosed` creates a new backoff policy and resets (zeroes) the stopwatch when `responseReceived`, then schedules the retry after `max(0, nextBackoffNanos() - elapsed)`, which is the initial backoff (~1 s with jitter) ([ControlPlaneClient.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/client/ControlPlaneClient.java#L475-L524)).
  - Go: the stream runner returns `backoff.ErrResetBackoff` when a message was received, and `RunF` then calls `timer.Reset(0)` and sets `attempt = 0`, so the next stream starts with no delay ([ads_stream.go](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/xds/clients/xdsclient/ads_stream.go#L240-L279), [backoff.go](https://github.com/grpc/grpc-go/blob/cbf30c4130/internal/xds/clients/internal/backoff/backoff.go#L101-L124)).
- **Prior documentation:**
  - gRFC A57: "If the ADS stream fails without having received a response from the server, the XdsClient must use exponential backoff for each successive attempt to establish the ADS stream, to avoid overloading the server. The backoff algorithm should be similar to what gRPC uses for connection attempts. The backoff state will be reset when an ADS stream attempt does finally receive a response from the server." It does not say whether the first attempt after a reset is delayed.
  - `doc/connection-backoff.md`: the first connection attempt is made immediately; backoff applies only between failed attempts.
- **Decision:** (a) keep the spec: initial backoff (~1 s) after a stream that received a response (C++, Java), (b) start the next stream immediately after a stream that received a response and use backoff only between attempts that receive nothing (Go; one reading of A57 and `doc/connection-backoff.md`), or (c) allow either.
- **Recommendation:** (a). Two of three implementations agree with it, and the delay keeps many clients from reconnecting to the management server all at once when it closes streams together (for example on restart or a `MAX_CONNECTION_AGE` wave). Bugs: Go (low): ADS stream restarts immediately after a stream that received a response.
- **Why this rank:** Changes only reconnect timing (about 1 s) after routine management-server stream rotation.

  - gRFC A54 (restrict control-plane status codes) lists "When applying a failed Config Selector result from the name resolver (an internal API for xDS in [gRFC A31][])". This assumes a resolver *may* produce a failing ConfigSelector result, which is consistent with Java's approach existing, but it doesn't require it.
  - doc/wait-for-ready.md: "gRPC implementations MAY provide a per-RPC option to not fail RPCs as a result of the channel being in `TRANSIENT_FAILURE` state. Instead, the implementation queues the RPCs until the channel is `READY`." Pending PR grpc/grpc#38953 (client channel), picker results: "Note, however, that if the RPC is [wait\_for\_ready], then it will be queued instead of being failed." These general semantics support option (a).
  - Pending PR grpc/grpc#38953 also says: "if a resolver returns an error for the service config and it has not previously returned a valid result to the channel, the channel will be placed into TRANSIENT\_FAILURE state, and RPCs that are not [wait\_for\_ready] will fail with that status."
  - No gRFC states the xDS resolver's error-result shape (searched A27, A28, A31, A47, A53, A54, A71, A74, A88).
- **Decision:** (a) no ConfigSelector, so wait_for_ready RPCs wait (C++/Go), or (b) an erroring ConfigSelector that fails all RPCs (Java).
- **Recommendation:** (a). Two of three implementations do this, and it follows normal wait_for_ready semantics: the error may be transient, and the RPC should wait for a fixed config. Java needs a fix.
- **Why this rank:** Java fails wait-for-ready RPCs on transient xDS config errors, against standard wait-for-ready semantics.

### XDS_LB-6. xds_cluster_impl: drops while not READY and drop_all → READY (language bug)

Only C++ applies EDS drops to every pick and reports READY when a category drops 100%. Go drops only while the child is READY, and Java never forces READY.

  - Java: drops on every pick, but reports the child's state unchanged, with no `drop_all` handling. ([ClusterImplLoadBalancer.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/ClusterImplLoadBalancer.java#L216-L223), [ClusterImplLoadBalancer.java](https://github.com/grpc/grpc-java/blob/ed3bf6b76b65fc76c1669ef70b71765844eb8a50/xds/src/main/java/io/grpc/xds/ClusterImplLoadBalancer.java#L409-L419))

  - Not covered by any prior documentation (searched: A27, A37, A74 for "drop"; A37 only says drops are handled by `xds_cluster_impl`).
- **Decision:** (a) keep the spec (always drop; `drop_all` → READY); (b) keep "always drop" but drop the READY requirement; (c) allow dropping only when the child is READY.
- **Recommendation:** (a). A control plane uses `drop_all` to shed all traffic for a cluster. That must work when the backends are down, and drops must not depend on connection state. Bugs: Go (medium): EDS drops not applied unless the child is READY, and no READY for drop_all. Java (low): drop_all does not report READY.

### XDS_SECURITY-3. `DownstreamTlsContext` validation gaps, mostly in Java (language bug)

Java doesn't NACK several invalid server TLS configs, and one of them leaves required mTLS unenforced. C++ accepts a validation context with no CA source.

(https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/source/common/listener_manager/lds_api.cc#L63-L119, https://github.com/envoyproxy/envoy/blob/a40510120eea1083a3300fc1dd2c3402f66cf26b/source/common/listener_manager/listener_manager_impl.cc#L587-L598)

- **Prior documentation:**
  - `doc/statuscodes.md`, codes generated by the library: "Incorrect Auth metadata ( Credentials failed to get metadata, Incompatible credentials set on channel and call, Invalid host set in `:authority` metadata, etc.) | UNAUTHENTICATED | Both"
  - gRFC A54 applies its check "When CallCredentials fail an RPC", and says only: "If an \"inappropriate status\" is detected, the status should be rewritten to use `INTERNAL` status code and include text within the status message making it clear a bug occurred." `UNAVAILABLE` and `UNAUTHENTICATED` are not in its list.
  - Otherwise not covered by any prior documentation (searched: L72, L126, AIP-4110, AIP-4111).
- **Decision:** (a) keep the spec: `UNAVAILABLE` when the token source can't be reached, `UNAUTHENTICATED` when it rejects the request (C++, Java's adapter). (b) Follow `doc/statuscodes.md`: every failure to get a token is `UNAUTHENTICATED` (Go's channel-level behavior). (c) Keep the spec's codes as SHOULD, and allow `UNAUTHENTICATED` when the implementation can't tell the two cases apart.
- **Recommendation:** (a). C++ and Java already tell the cases apart, and the general rule in [Call Credentials: Results](06-security/03-call-credentials.md#13-results) says the same. `UNAVAILABLE` lets retry policies treat a metadata server or token endpoint blip as transient. `UNAUTHENTICATED` tells the application that its credentials are wrong. `INTERNAL` and `UNKNOWN` are never right for a fetch failure. Bugs: Go (low): Google call credentials fail RPCs with `UNAUTHENTICATED` (channel-level) or `INTERNAL` (per-call) when the token source is unreachable or returns a 5xx or 429 status. C++ (low): external account credentials fail RPCs with `UNKNOWN` when the HTTP request to the token source fails. Java (low): `ComputeEngineChannelCredentials` fails every RPC with `INTERNAL` off GCP. Docs (low): `doc/statuscodes.md` lists `UNAUTHENTICATED` for every credential failure to get metadata.
- **Why this rank:** Only the status code differs; the RPC fails either way. The code matters to retry policies, which usually retry `UNAVAILABLE` but not `UNAUTHENTICATED`, and to monitoring that treats `UNAUTHENTICATED` as misconfiguration.
