# gRPC Spec: Optionality Notes

Working notes for the [gRPC specification](spec/README.md).

The spec does not say which features are optional. Apart from the wire
protocol, almost everything in gRPC is optional in practice. This file records
features that we have noticed are missing from, or only partly provided by,
some implementations. If we later decide to define conformance levels or
mark features as optional, these notes are the starting point.

Format: `- <feature> (<spec section link>): <observation>`

## Core RPC semantics and API

- Per-call authority override ([Core RPC Semantics](spec/02-rpc-semantics/README.md), [Channel](spec/04-client-channel/02-channel.md)): doc/internationalization.md and gRFC A81 note that not every implementation exposes a per-call authority override.
- Compression algorithms ([Core RPC Semantics](spec/02-rpc-semantics/README.md)): the set of supported algorithms varies; `identity` and `gzip` are universal, `deflate` is not everywhere, and `snappy` appears only in the PROTOCOL-HTTP2.md grammar.
- Channel and server default compression algorithm, and compression levels ([Core RPC Semantics: Configuration and Precedence](spec/02-rpc-semantics/README.md#134-configuration-and-precedence)): Java has no channel or server default algorithm (only per call) and no compression levels. Go sets a channel default only through default call options, has no server default except a deprecated option, and has no compression levels. Only C++ provides all of them.
- Per-call maximum send and receive message size limits on the client ([Core RPC Semantics: Message Size Limits](spec/02-rpc-semantics/README.md#12-message-size-limits)): supported in Go (`grpc.MaxCallRecvMsgSize`, `grpc.MaxCallSendMsgSize`) and Java (`CallOptions.withMaxInboundMessageSize`, `CallOptions.withMaxOutboundMessageSize`); not supported per call on C++ `grpc::ClientContext` (channel and server level only).
- Custom compressor registration ([Core RPC Semantics: Compression](spec/02-rpc-semantics/README.md#13-compression)): supported in Go (`encoding.RegisterCompressor`) and Java (`CompressorRegistry`, `DecompressorRegistry`); not supported in C++ (fixed `identity`, `deflate`, `gzip` enum). Also note that `deflate` is built-in only in C++ (absent in Go and Java), and Go registers `gzip` only when `google.golang.org/grpc/encoding/gzip` is imported.

## Wire protocol

- True binary metadata (gRFC G1) ([True Binary Metadata](spec/03-wire-protocol/02-true-binary-metadata.md)): experimental and implemented only in C++; not implemented in Java or Go.
- HTTP/3 transport (gRFC G2) ([gRPC over HTTP/3](spec/03-wire-protocol/03-http3.md)): not implemented in C++, Java, or Go (only an experimental implementation exists in `grpc-dotnet` outside those three).
- Configurable `MAX_PING_STRIKES` ([HTTP/2 Server Transport: Ping Enforcement](spec/05-server/02-transports/02-http2.md#72-ping-enforcement)): only C++ makes it configurable; Java and Go hardcode 2.
- Server-side `TCP_USER_TIMEOUT` ([HTTP/2 Server Transport: TCP_USER_TIMEOUT](spec/05-server/02-transports/02-http2.md#73-tcp_user_timeout)): not implemented in Java. Java sets it only on client channels (Netty epoll, keepalive enabled).
- Rejecting unknown content-subtypes with `UNIMPLEMENTED` ([Core RPC Semantics](spec/02-rpc-semantics/README.md), [Server](spec/05-server/README.md)): not implemented in Java, Go, or C++; all three ignore the subtype and decode with the method's codec.
- Validating `grpc-status-details-bin` against `grpc-status` ([gRPC over HTTP/2](spec/03-wire-protocol/01-http2.md)): not implemented in C++; Java checks only in its protobuf status helper, not in the core library.

## Client channel

- Public custom name resolver and LB policy registration APIs ([Name Resolution](spec/04-client-channel/03-name-resolution.md), [Load Balancing](spec/04-client-channel/06-load-balancing.md)): Java and Go expose public extension APIs; C++ (`grpcpp`) keeps its custom resolver and LB policy registries internal to C-core.
- Reading the channel's current service config ([Service Config](spec/04-client-channel/04-service-config.md)): C++ exposes the full active service config JSON (`ChannelInterface::GetServiceConfigJSON()`); Go exposes only per-method lookup (`ClientConn.GetMethodConfig(method)`); Java `ManagedChannel` has no public getter (available via Channelz).
- Per-channel resolver factories without global registration ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): supported in Go (`grpc.WithResolvers`) and deprecated in Java (`ManagedChannelBuilder.nameResolverFactory`); not exposed in C++ public `ChannelArguments`.
- Waiting for a connectivity state change with a deadline or cancellation ([Channel](spec/04-client-channel/02-channel.md)): supported in C++ (`WaitForStateChange(last_observed, deadline)`) and Go (`WaitForStateChange(ctx, sourceState)`); Java's callback-based `ManagedChannel.notifyWhenStateChanged(source, callback)` takes no deadline or cancellation handle.
- Changing the default target scheme process-wide ([Channel](spec/04-client-channel/02-channel.md)): Go has an explicit setter (`resolver.SetDefaultScheme`, from gRFC L9); in Java the default scheme is that of the highest-priority provider in `NameResolverRegistry.getDefaultRegistry()`, so registering a higher-priority `NameResolverProvider` changes it; C++ (`grpcpp`) has no public API for it (the default prefix is set only through the internal C-core resolver registry builder).
- Resetting connection backoff from the channel API ([Channel](spec/04-client-channel/02-channel.md), [Load Balancing](spec/04-client-channel/06-load-balancing.md), [Subchannels and Connections](spec/04-client-channel/07-subchannels.md)): public in C++ (`experimental::ChannelResetConnectionBackoff`), Java (`ManagedChannel.resetConnectBackoff()`), and Go (`(*ClientConn).ResetConnectBackoff()`), whereas `ResetBackoff()` on the LB policy and LB subchannel helper interfaces is C++-only (Java and Go reset subchannels directly at the channel layer and do not reset LB-policy-owned control channels such as `rls`). None of the three implementations currently resets the name resolver's backoff from this call.
- Separate default-LB-policy channel option ([Channel](spec/04-client-channel/02-channel.md)): some implementations have one; the spec uses the default service config instead.
- `dns` resolver minimum time between resolutions ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): configurable per-channel in C++ (`GRPC_ARG_DNS_MIN_TIME_BETWEEN_RESOLUTIONS_MS`), process-wide in Go (`resolver.SetMinResolutionInterval`), and via JVM system property `networkaddress.cache.ttl` in Java (which drops rather than delays early refreshes).
- `ipv4:` / `ipv6:` target schemes ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): C++ only (`SockaddrResolver`); not in Java or Go. (Go instead provides a `passthrough:` resolver from gRFC L9, absent in C++ and Java.)
- `unix:` target scheme ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): C++ and Go built-in on Unix-like systems; in Java, provided by `io.grpc.netty.UdsNameResolverProvider` (Netty transport artifact only).
- Address-mapping proxy environment variables (a proxy address plus the address ranges that use it) ([HTTP CONNECT Proxy Support](spec/04-client-channel/09-proxy.md)): provided by some implementations only; not in the spec.
- Private subchannel pool option ([Subchannels and Connections](spec/04-client-channel/07-subchannels.md)): only meaningful for implementations that share subchannels between channels.
- Per-channel retry buffer limit ([Retries and Hedging](spec/04-client-channel/12-retries.md#71-buffer-limits)): not implemented in Go or C++. Both have only a per-RPC limit (256 KiB default); Java has both.
- `connectionScaling` service config field ([Service Config](spec/04-client-channel/04-service-config.md)): not implemented in Java or Go (the field is ignored as unknown). None of the three implements the xDS `per_host_thresholds` max_connections part.
- `unix-abstract:` target scheme ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): C++ and Go (Linux); not implemented in Java.
- `vsock:` target scheme ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): C++ only (Linux); not implemented in Java or Go.
- Resolver-level option to disable service config lookup ([Name Resolution](spec/04-client-channel/03-name-resolution.md#3-channel-handling-of-resolver-results)): Java and Go apply the option at the channel level. The channel discards the service config (and config selector) from every resolver, which breaks xDS when the option is set. Only C++ limits it to resolvers that fetch a published config (DNS TXT).
- DNS-server authority in `dns:` targets ([Name Resolution](spec/04-client-channel/03-name-resolution.md)): not implemented in Java (silently ignored); C++ supports it only with c-ares (literal `IP:port`), and the native resolver ignores it.
- DNS TXT service config lookup ([Name Resolution: `dns`](spec/04-client-channel/03-name-resolution.md#71-dns)): the spec says it SHOULD be off by default. It is off by default in Java and C++. Go enables it by default (`GRPC_ENABLE_TXT_SERVICE_CONFIG` defaults to `true`) and can't change that default without breaking compatibility.
- Proxy environment variables ([HTTP CONNECT Proxy Support](spec/04-client-channel/09-proxy.md)): not implemented in Java, which uses the platform proxy selector instead. Go reads only `HTTPS_PROXY`/`https_proxy` and `NO_PROXY`/`no_proxy`.
- In-process transport ([In-Process Client Transport](spec/04-client-channel/08-transports/04-in-process.md), [In-Process Server Transport](spec/05-server/02-transports/04-in-process.md)): not implemented in Go (`test/bufconn` is an in-memory connection used with the HTTP/2 transport, not a separate transport).
- Hedging ([Retries and Hedging](spec/04-client-channel/12-retries.md#3-hedging-policy)): not implemented in C++ or Go; neither parses `hedgingPolicy` (gRFC A6 lists "Go except hedging, and C-Core except hedging"). Java implements it.
- Configurable Happy Eyeballs Connection Attempt Delay ([`pick_first` LB Policy](spec/04-client-channel/lb-policies/pick_first.md#21-other-inputs)): only C++ lets the application set it; Java and Go hardcode 250 ms.
- `least_request` LB policy ([`least_request` LB Policy](spec/04-client-channel/lb-policies/least_request.md)): not implemented in C++.
- `random_subsetting` LB policy ([`random_subsetting` LB Policy](spec/04-client-channel/lb-policies/random_subsetting.md)): not implemented in C++.
- `ring_hash` endpoint `hash_key` and `requestHashHeader` (gRFC A76) ([`ring_hash` LB Policy](spec/04-client-channel/lb-policies/ring_hash.md#2-configuration)): Java does not implement the endpoint `hash_key`, and its `requestHashHeader` support is off by default behind `GRPC_EXPERIMENTAL_RING_HASH_SET_REQUEST_HASH_KEY`.
- WRR custom utilization metrics (gRFC A114) ([`weighted_round_robin` LB Policy: Custom Utilization Metrics](spec/04-client-channel/lb-policies/weighted_round_robin.md#custom-utilization-metrics)): not implemented in Go. Java has it behind `GRPC_EXPERIMENTAL_WRR_CUSTOM_METRICS` (default off).
- Client-side health checking under every petiole policy ([Client-Side Health Checking: Where Health Checking Applies](spec/04-client-channel/10-health-checking.md#2-where-health-checking-applies)): Java health-checks only under `round_robin` (or custom policies that wrap themselves); `weighted_round_robin`, `least_request`, and `ring_hash` never health-check, and the stream runs whether or not a health watcher is registered.
- Picker-supplied `:authority` override (gRFC A81) ([Load Balancing: Authority Override](spec/04-client-channel/06-load-balancing.md#66-authority-override)): in Go, xDS authority rewriting is gated behind `GRPC_EXPERIMENTAL_XDS_AUTHORITY_REWRITE=true` (off by default), and Go's public `balancer.PickResult` does not expose a dedicated authority-override field for custom LB policies (uses internal `PickResult.Metadata` `:authority`). In Java, `ClusterImplLoadBalancer.enableXdsAuthorityRewrite` also defaults `GRPC_EXPERIMENTAL_XDS_AUTHORITY_REWRITE` to `false`.
- HTTP CONNECT proxy API options (gRFC A1) ([HTTP CONNECT Proxy Support: API Requirements](spec/04-client-channel/09-proxy.md#6-api-requirements)): per-channel explicit proxy address option is supported in C++ (`GRPC_ARG_HTTP_PROXY`) and Java (`ManagedChannelBuilder.proxyDetector`) but not in Go (provides `grpc.WithNoProxy()` and `http.ProxyFromEnvironment`); custom proxy mapper API for both name and address mapping is internal-only in C++ (`ProxyMapperInterface`) and Go (`delegatingresolver`) while Java `io.grpc.ProxyDetector` is public; proxy credentials via URI `userinfo` are supported in C++ and Go while Java requires `java.net.Authenticator` or `HttpConnectProxiedSocketAddress.Builder.setUsername`/`setPassword`.
- Client-side health checking disable option and Go package registration (gRFC A17) ([Client-Side Health Checking](spec/04-client-channel/10-health-checking.md)): C++ (`GRPC_ARG_INHIBIT_HEALTH_CHECKING`) and Go (`grpc.WithDisableHealthCheck()`) provide a channel option to disable client-side health checking when `healthCheckConfig` is present in the service config; Java provides no channel builder option to disable health checking independently of disabling service config lookup. Additionally, enabling client-side health checking in Go requires side-effect importing `google.golang.org/grpc/health`.
- Client-side backend metric consumer APIs (gRFC A51) ([Client-Side Backend Metrics (ORCA)](spec/04-client-channel/11-backend-metrics.md)): in C++, per-call and OOB backend metric consumer APIs (`BackendMetricData`, `OobBackendMetricWatcher`) are C-core internal rather than public `grpc::` C++ APIs. In Go, per-call ORCA trailer parsing requires importing `google.golang.org/grpc/orca`.
- Client-received `grpc-previous-rpc-attempts` metadata (gRFC A6) ([Retries and Hedging: `grpc-previous-rpc-attempts`](spec/04-client-channel/12-retries.md#9-grpc-previous-rpc-attempts)): exposing `grpc-previous-rpc-attempts` in client-received initial metadata (`MAY` in spec/A6) is not implemented in C++, Java, or Go (all three set it only on outgoing request headers).
- `pick_first` `READY` → `CONNECTING`/`TRANSIENT_FAILURE` subchannel recreation (gRFC A105) ([`pick_first` LB Policy](spec/04-client-channel/lb-policies/pick_first.md)): only C++ implements subchannel connection scaling (`A105`) where a `READY` subchannel can transition directly to `CONNECTING` or `TRANSIENT_FAILURE`; in Java and Go, subchannels exit `READY` only via `IDLE`, so `pick_first` does not need or implement the `READY` → `CONNECTING`/`TRANSIENT_FAILURE` subchannel-recreation path.
- `priority` configurable failover timeout ([`priority` LB Policy](spec/04-client-channel/lb-policies/priority.md)): configurable failover timer duration exists only in C++ (`GRPC_ARG_PRIORITY_FAILOVER_TIMEOUT_MS` / `"grpc.priority_failover_timeout_ms"`, internal/test channel arg); Java (`PriorityLoadBalancer`) and Go (`balancer/priority`) hardcode the 10-second default.

## Server

- Server-side response cardinality check ([Server](spec/05-server/01-server.md#33-status-and-trailers)): not implemented in Go (a client-streaming handler can end with OK and no response) or C++ (APIs always send a response with OK; the generic API has no check). Java detects it but resets the stream instead of sending INTERNAL.
- Maximum send (response) message size option ([Server Behavior](spec/05-server/01-server.md#24-limits)): not available in Java (`ServerBuilder` has only `maxInboundMessageSize`), although the API requirements call for one.

## Security

- Audit logging for authorization (gRFC A59) ([Authorization](spec/06-security/04-authorization.md), [xDS HTTP Filters](spec/09-xds/07-http-filters.md)): not implemented in Java (neither gRPC authorization policy `audit_logging_options` nor xDS RBAC `audit_logging_options` is supported, and there is no audit logger API). In C++, gRPC authorization policy audit logging is enabled unconditionally, while xDS RBAC `audit_logging_options` is off by default behind `GRPC_EXPERIMENTAL_XDS_RBAC_AUDIT_LOGGING`. Go enables both unconditionally.
- TLS private key offloading (gRFC A107) ([TLS: Private Key Offloading](spec/06-security/02-tls.md#11-private-key-offloading)): implemented only in C++; not implemented in Java or Go.
- CRL verification and public `CertificateProvider` API (gRFC A69) ([TLS: Certificate Revocation Lists](spec/06-security/02-tls.md)): CRL directory reloading and public `CertificateProvider` APIs are available in C++ and Go; Java does not expose a public `CertificateProvider` API or directory-watched CRL provider on standard TLS credentials.
- TLS key exchange group configuration (gRFC A120) ([TLS: Key Exchange Groups](spec/06-security/02-tls.md#12-key-exchange-groups)): not available in Java, which has no API to set the groups and does not expose the negotiated group; only its S2A credentials set a groups list.
- JWT token file call credentials ([Call Credentials](spec/06-security/03-call-credentials.md#4-jwt-token-file-credentials), [Bootstrap](spec/09-xds/02-bootstrap.md#41-xdsserver-object)): the spec makes these a MAY and leaves their details (whitespace handling, caching, expired tokens) mostly implementation-defined, deferring to gRFC A97. Off by default behind `GRPC_EXPERIMENTAL_XDS_BOOTSTRAP_CALL_CREDS` in C++ and Go for bootstrap `call_creds`; not implemented in Java (`GrpcBootstrapperImpl.parseCallCredentials` returns nothing, so bootstrap `call_creds` entries are ignored).
- GCP service account identity call credentials ([GCP Service Account Identity Credentials](spec/10-vendor-specific/03-gcp-service-account-identity-credentials.md)): Go added them in v1.83.0 (`credentials/google`). Java's GCP authentication filter uses google-auth `IdTokenCredentials` (`ComputeEngineCredentials`) instead of a gRPC implementation of the [token-fetching algorithm](spec/06-security/03-call-credentials.md#33-algorithm).
- Composite channel and call credential wrapper types ([Security Model: Composite Credentials](spec/06-security/01-security-model.md#4-composite-credentials)): C++ and Java provide `CompositeChannelCredentials` and `CompositeCallCredentials`; Go attaches channel-level call credentials via repeatable `grpc.WithPerRPCCredentials` dial options (or `credentials.Bundle`) rather than standalone composite credential types.
- Server-side multi-certificate SNI selection ([TLS: Server Name Indication (SNI)](spec/06-security/02-tls.md#2-server-name-indication-sni), [TLS: Model](spec/06-security/02-tls.md#61-model)): C++ (`TlsServerCredentialsOptions` / `InMemoryCertificateProvider`) and Go (`crypto/tls.Config.Certificates` and `advancedtls`) support configuring multiple server identity certificates selected by client SNI; Java's `TlsServerCredentials.Builder` and `FileWatcherCertificateProvider` accept only a single server certificate chain and private key.
- ALTS handshaker service address override ([ALTS: Handshaker Service](spec/06-security/05-alts.md#2-handshaker-service)): public option in Go (`ClientOptions`/`ServerOptions.HandshakerServiceAddress`); testing-only setter in Java (`setHandshakerAddressForTesting`); C++ has only the core-internal `grpc_alts_credentials_create_customized`.
- ALTS integrity-only record protocol and handshaker extras ([ALTS](spec/06-security/05-alts.md)): only C++ can offer `ALTSRP_GMAC_128` (internal options API), send `access_token` (hard-bound tokens, gRFC L126) and `transport_protocol_preferences`; Go and Java offer only `ALTSRP_GCM_AES128_REKEY`.

## Standard services

- Server Reflection `v1alpha` co-registration ([Server Reflection: API Requirements](spec/07-services/02-reflection.md#7-api-requirements)): C++ (`ProtoServerReflectionPlugin`) and Go (`reflection.Register`) register both `v1` and `v1alpha` together; Java's `ProtoReflectionServiceV1` registers only `v1` (deprecated `ProtoReflectionService` registers `v1alpha` separately). C++ and Go answer descriptor queries from the process-wide generated descriptor pool by default, whereas Java indexes only descriptors of services registered on that `Server`.
- Server Reflection custom descriptor source ([Server Reflection: API Requirements](spec/07-services/02-reflection.md#7-api-requirements)): supported in Go (`reflection.ServerOptions{Services, DescriptorResolver, ExtensionResolver}`); not exposed in C++ or Java.
- Client-side reflection descriptor database ([Server Reflection: API Requirements](spec/07-services/02-reflection.md#7-api-requirements)): not implemented in Java or Go; C++ has `ProtoReflectionDescriptorDatabase` only as a test utility (used by `grpc_cli`, not an installed public header), which currently speaks `v1alpha` only.
- Health status manager operations ([Health Service: API Requirements](spec/07-services/01-health.md#7-api-requirements)): "remove a service" is implemented only in Java (`HealthStatusManager.clearStatus`), not in C++ or Go; "leave shutdown" is implemented only in Go (`health.Server.Resume()`, which also resets all registered services to `SERVING`), not in C++ or Java.
- Health `List` RPC ([Health Service](spec/07-services/01-health.md)): not implemented in Java, C++. Go implements it with the 100-entry limit.
- ORCA per-server recorder `setAllUtilization` bulk operation ([Backend Metrics (ORCA)](spec/07-services/03-orca.md#3-per-server-recorder)): not implemented in Go (only per-name set/delete).
- Admin interface xDS dependency isolation ([Admin Interface](spec/07-services/04-admin.md)): Java (`Class.forName`) and Go (`xds` package `init()` hook) include CSDS only when xDS is linked; C++'s Bazel `grpcpp_admin` target unconditionally depends on `//:grpcpp_csds` unless built with `--define grpc_no_xds=true`, and CMake has no installable `grpc++_admin` target.

## Observability

- Disabling Channelz tracking per channel or server ([Channelz](spec/08-observability/06-channelz.md#10-api-requirements)): C++ has `GRPC_ARG_ENABLE_CHANNELZ` for channels, subchannels, and servers. Java has no per-channel or per-server control. Go has none either: collection is process-wide and turns on when the channelz service package is linked in.
- Custom binary log sink API ([Binary Logging](spec/08-observability/07-binary-logging.md#6-sinks-and-call-ids)): Java has `BinaryLogs.createBinaryLog(BinaryLogSink, String)` and Go has `binarylog.SetSink` (experimental). C++ has no binary logging.
- Binary logging ([Binary Logging](spec/08-observability/07-binary-logging.md)): not implemented in C++. Java enables it only through code (no automatic env-var activation). Go configures filter strings publicly only via the `GRPC_BINARY_LOG_FILTER` environment variable (no public API option accepting a configuration string; `NewLoggerFromConfigString` is internal).
- Stats plugin scoping ([Metrics Framework and OpenTelemetry Plugin](spec/08-observability/03-metrics-framework.md)): implementations provide a global scope predicate, per-channel registration, or both; the spec describes both.
- `grpc.client.call.duration` per-call metric ([Metric Catalog](spec/08-observability/04-metrics.md)): not implemented in C++ (its OpenTelemetry plugin's default set has the other 8 per-call metrics).
- Retry metrics ([Metric Catalog](spec/08-observability/04-metrics.md)): not implemented in Go. `grpc.client.call.hedges` is also not implemented in C++.
- Generic method attribute predicate ([Metrics Framework and OpenTelemetry Plugin](spec/08-observability/03-metrics-framework.md)): not implemented in Java. Go has one on the server only, applied to all methods.
- Outlier detection metrics (gRFC A91) ([`outlier_detection` LB Policy](spec/04-client-channel/lb-policies/outlier_detection.md#6-metrics), [Metric Catalog: Outlier Detection LB Policy Metrics](spec/08-observability/04-metrics.md#9-outlier-detection-lb-policy-metrics)): not implemented in Java (C++ and Go emit them).
- TLS telemetry metrics (gRFC A118) ([Metric Catalog: TLS Metrics](spec/08-observability/04-metrics.md#7-tls-metrics)): C++ implements `grpc.client.tls.handshakes` and `grpc.server.tls.handshakes` (behind default-off experiment `otel_export_telemetry_domains`); the three TLS offload duration histograms in C++ and all five TLS metrics in Java and Go are not yet implemented.
- OpenTelemetry tracing (gRFC A72) ([Tracing](spec/08-observability/05-tracing.md)): in Java, OpenTelemetry span creation is off by default behind `GRPC_EXPERIMENTAL_ENABLE_OTEL_TRACING` even when a `TracerProvider` is configured on `GrpcOpenTelemetry`.
- TCP metrics (gRFC A80) ([Metric Catalog: TCP Metrics](spec/08-observability/04-metrics.md#10-tcp-metrics)): not implemented in Go. Java registers only `grpc.tcp.min_rtt`, `connections_created`, `connection_count`, `packets_retransmitted`, and `recurring_retransmits`. C++ registers the rest but not `grpc.tcp.connections_created`, records `min_rtt` and the latency metrics as integer microseconds (units `{us}`/`us`), and uses separate `grpc.tcp.transfer_latency_<size>` metrics (including an extra 8 MiB size) instead of one metric with a `grpc.transfer_size` label. The metrics are experimental, so these differences are not filed as bugs.
- `ChannelData.max_connections_per_subchannel` channelz field ([Channelz: Channel and Subchannel Data](spec/08-observability/06-channelz.md#4-channel-and-subchannel-data)): Java and Go do not implement connection scaling, so they have no value to report. (C++ implements connection scaling but does not populate the field; that is recorded as a bug.)

## xDS

- Programmatic bootstrap configuration ([Bootstrap](spec/09-xds/02-bootstrap.md)): the spec makes programmatic override a MAY (`XDS_BOOTSTRAP-1`); C++, Go, and Java all provide a programmatic bootstrap API.
- `allowed_grpc_services` bootstrap field ([Bootstrap: Allowed gRPC Service Object](spec/09-xds/02-bootstrap.md#45-allowed-grpc-service-object)): C++ and Go parse and validate it only when an experimental feature that consumes it is enabled, and otherwise ignore it; Java always validates it. No consumer (ext_authz, ext_proc) is in the spec yet.
- Stateful session affinity xDS HTTP filter ([xDS HTTP Filters](spec/09-xds/07-http-filters.md)): not implemented in Java or Go.
- GCP Authentication xDS HTTP filter (gRFC A83) ([GCP Authentication Filter](spec/10-vendor-specific/04-gcp-authentication-filter.md)): not in any Go release (latest v1.85.0). The filter code shipped in v1.83.0, but it is registered only on master (unreleased), and reading the audience from cluster metadata is still behind `GRPC_EXPERIMENTAL_XDS_GCP_AUTHENTICATION_FILTER` (default false).
- xDS HTTP CONNECT (gRFC A86, `Http11ProxyUpstreamTransport` and `Address` proxy metadata) ([Cluster: `Http11ProxyUpstreamTransport`](spec/09-xds/04-resources/04-cluster.md#61-http11proxyupstreamtransport), [xDS Security: HTTP CONNECT and TLS](spec/09-xds/09-security.md#6-http-connect-and-tls)): off by default behind `GRPC_EXPERIMENTAL_XDS_HTTP_CONNECT` in C++, Java, and Go (when disabled, all three NACK a `Cluster` whose `transport_socket` uses `Http11ProxyUpstreamTransport` and ignore `Address` proxy metadata).
- HttpFilter.disabled / FilterConfig.disabled ([xDS HTTP Filters](spec/09-xds/07-http-filters.md)): not in the spec; honored by C++, only behind experimental guards in Go, not implemented in Java.
- LbEndpointCollection (LEDS list collections) and `leds_cluster_locality_config` ([ClusterLoadAssignment and LbEndpointCollection](spec/09-xds/04-resources/05-endpoint.md), [Client Data Plane: Watch graph](spec/09-xds/05-client.md#22-watch-graph), [`cds` LB Policy: Endpoint List and Attributes](spec/09-xds/lb-policies/cds.md#endpoint-list-and-attributes)): not implemented in Java, Go, or C++. Behavior (validation, duplicate-address scope, locality proxy-address fallback) comes from gRFC A95 only.
- `xds_override_host` LB policy, `Cluster.upstream_config` (`HttpProtocolOptions.idle_timeout`), and `DRAINING` endpoint retention (gRFCs A55, A75) ([`xds_override_host` LB Policy](spec/09-xds/lb-policies/xds_override_host.md), [Cluster: Upstream Connection Options](spec/09-xds/04-resources/04-cluster.md#8-upstream-connection-options), [ClusterLoadAssignment](spec/09-xds/04-resources/05-endpoint.md)): implemented only in C++. Java and Go do not register `xds_override_host_experimental` or parse/validate `Cluster.upstream_config`, and Java treats `LbEndpoint.health_status == DRAINING` as unhealthy in EDS parsing.
- `VirtualHost.retry_policy` ([RouteConfiguration](spec/09-xds/04-resources/03-route-configuration.md)): not implemented in Java. Only the route-level `RouteAction.retry_policy` is parsed there, so a virtual-host retry policy is ignored.
- `xds.endpoint.supports_lb_endpoint_collection` client feature ([xDS / Proxyless Service Mesh Support](spec/09-xds/01-architecture.md#3-client-features)): not sent by Java, Go, or C++ (goes with the unimplemented LbEndpointCollection support from A95).
- `fail_on_data_errors` and `resource_timer_is_transient_error` server features and the A88 data-error handling ([Bootstrap](spec/09-xds/02-bootstrap.md#5-server-features), [XdsClient](spec/09-xds/03-xds-client.md#7-error-handling)): default-off behind `GRPC_EXPERIMENTAL_XDS_DATA_ERROR_HANDLING` in C++ and Java; not implemented in Go (Go still gives `ignore_resource_deletion` its older effect). In addition, `DiscoveryResponse.resource_errors` and CSDS `RECEIVED_ERROR` are not implemented in Java or Go.
- `fallback_on_reachability_only` bootstrap field (gRFC A95) ([Bootstrap](spec/09-xds/02-bootstrap.md#3-top-level-fields), [XdsClient](spec/09-xds/03-xds-client.md#8-fallback)): default-off behind `GRPC_EXPERIMENTAL_XDS_ENDPOINT_FALLBACK` in C++ and Java; not implemented in Go.
- Rejecting an unset `weighted_clusters` weight ([RouteConfiguration](spec/09-xds/04-resources/03-route-configuration.md)): SHOULD per the spec (matches Envoy); C++ rejects, but Java and Go treat an unset weight as 0. Known, allowed deviation.
- RandomSubsetting xDS LB policy converter (gRFC A68) ([xDS LB Policies: `load_balancing_policy`](spec/09-xds/06-lb-policies.md#21-load_balancing_policy)): not registered in Java, Go, or C++. Java and Go ship the `random_subsetting` policy but their xDS converters have no `RandomSubsetting` branch; C++ has no `random_subsetting` policy. A Cluster whose only policy is `RandomSubsetting` is NACKed, and one that lists a fallback after it uses the fallback.
- `LeastRequest` xDS LB policy converter and legacy `LEAST_REQUEST` `lb_policy` ([xDS LB Policies: `load_balancing_policy`](spec/09-xds/06-lb-policies.md#21-load_balancing_policy), [xDS LB Policies: Legacy `lb_policy`](spec/09-xds/06-lb-policies.md#22-legacy-lb_policy)): not supported in C++, which has no `least_request` policy. The `LeastRequest` converter is not registered, and a Cluster with the legacy `LEAST_REQUEST` enum is NACKed.
- gRFC A75 LB policy tree ([`cds` LB Policy: Position in the xDS LB Policy Tree](spec/09-xds/lb-policies/cds.md#11-position-in-the-xds-lb-policy-tree)): implemented in full only in C++. Java runs `outlier_detection` and `xds_cluster_impl` once per priority; Go follows A75 for non-aggregate clusters (since v1.85.0) but still flattens aggregate clusters and uses the aggregate cluster's LB policy for all leaves.
- xDS connection scaling (`per_host_thresholds` / `max_connections_per_subchannel`, gRFC A105) ([Cluster: Circuit Breakers](spec/09-xds/04-resources/04-cluster.md#3-circuit-breakers), [xDS LB Policies](spec/09-xds/06-lb-policies.md), [`xds_cluster_impl` LB Policy: Connection Scaling](spec/09-xds/lb-policies/xds_cluster_impl.md#connection-scaling)): not implemented in C++, Java, or Go.
- xDS dualstack endpoints (`Endpoint.additional_addresses`, gRFC A61) ([ClusterLoadAssignment and LbEndpointCollection: LbEndpoint](spec/09-xds/04-resources/05-endpoint.md#3-lbendpoint)): enabled by default in C++ and Go; off by default in Java behind `GRPC_EXPERIMENTAL_XDS_DUALSTACK_ENDPOINTS`.
- xDS authority rewriting (`auto_host_rewrite`, gRFC A81) ([Client Data Plane: Authority rewriting](spec/09-xds/05-client.md#59-authority-rewriting), [`xds_cluster_impl` LB Policy: Authority Rewriting](spec/09-xds/lb-policies/xds_cluster_impl.md#authority-rewriting)): enabled unconditionally in C++; off by default behind `GRPC_EXPERIMENTAL_XDS_AUTHORITY_REWRITE` in Go and in Java's `ClusterImplLoadBalancer` (where `XdsRouteConfigureResource` defaults the same flag to `true`).
- xDS mTLS SPIFFE trust bundle map (gRFC A87) ([xDS Security: `file_watcher` Plugin](spec/09-xds/09-security.md#51-file_watcher-plugin)): off by default behind `GRPC_EXPERIMENTAL_XDS_MTLS_SPIFFE` in C++, Java, and Go.
- xDS system root certificates (gRFC A82) ([xDS Security: `UpstreamTlsContext` Validation](spec/09-xds/09-security.md#22-upstreamtlscontext-validation)): enabled by default in C++ and Java; off by default in Go behind `GRPC_EXPERIMENTAL_XDS_SYSTEM_ROOT_CERTS`.
- xDS SNI and `auto_sni_san_validation` (gRFC A101) ([xDS Security: SNI Selection](spec/09-xds/09-security.md#23-sni-selection), [xDS Security: Server Identity Verification](spec/09-xds/09-security.md#3-server-identity-verification)): enabled by default in C++ and Java; off by default in Go behind `GRPC_EXPERIMENTAL_XDS_SNI`.

## Vendor-specific features

- `google-c2p` resolver registration ([Google Cloud-to-Prod (`google-c2p`) Resolver](spec/10-vendor-specific/02-google-c2p-resolver.md)): registered by default in C++ (unless built with `GRPC_NO_XDS`) and in Java when `grpc-googleapis` is on the classpath; Go requires importing `google.golang.org/grpc/xds/googledirectpath`. C++ and Java also register the alias scheme `google-c2p-experimental`. Go alone lets applications change the universe domain of the Traffic Director URI (`googledirectpath.SetUniverseDomain`).
- Google default credentials hard-bound ALTS call credentials (gRFC L126) ([Google Default Credentials: ALTS-Specific Call Credentials](spec/10-vendor-specific/01-google-default-credentials.md#33-alts-specific-call-credentials)): only C++ can create them automatically (`create_hard_bound_credentials`, which adds `transport=alts` to the compute engine token request); all three accept application-supplied ALTS-specific call credentials.
- Compute engine channel credentials ([Google Default Credentials: Compute Engine Channel Credentials](spec/10-vendor-specific/01-google-default-credentials.md#5-compute-engine-channel-credentials)): dedicated APIs in Java (`ComputeEngineChannelCredentials`) and Go (`google.NewComputeEngineCredentials`); C++ has none (applications pass `GoogleComputeEngineCredentials()` to Google default credentials).
- Google call credentials in general ([Google Call Credentials](spec/10-vendor-specific/05-google-call-credentials.md)): C++ implements every type it ships inside gRPC (token fetch, caching, and ADC lookup in `src/core/credentials`). Java ships no Google call credential types of its own: applications create google-auth-library-java `Credentials` and wrap them with `MoreCallCredentials.from`. Go wraps `golang.org/x/oauth2/google` in `credentials/oauth`. In Java and Go, caching and refresh are therefore those of the auth library.
- Application Default Credentials as standalone call credentials ([Google Call Credentials: Application Default Credentials](spec/10-vendor-specific/05-google-call-credentials.md#2-application-default-credentials)): Go `oauth.NewApplicationDefault`; Java `MoreCallCredentials.from(GoogleCredentials.getApplicationDefault())`; C++ has no standalone API (ADC is used only inside `GoogleDefaultCredentials()`).
- Compute engine call credentials ([Google Call Credentials: Compute Engine Credentials](spec/10-vendor-specific/05-google-call-credentials.md#3-compute-engine-credentials)): C++ `GoogleComputeEngineCredentials()`; Go `oauth.NewComputeEngine()`; Java via google-auth `ComputeEngineCredentials`. Only C++ provides the ALTS hard-bound variant ([Google Call Credentials: ALTS Hard-Bound Compute Engine Credentials](spec/10-vendor-specific/05-google-call-credentials.md#31-alts-hard-bound-compute-engine-credentials)).
- Service account JWT access credentials ([Google Call Credentials: Service Account JWT Access Credentials](spec/10-vendor-specific/05-google-call-credentials.md#4-service-account-jwt-access-credentials)): C++ `ServiceAccountJWTAccessCredentials`; Go `oauth.NewJWTAccessFromKey` / `NewJWTAccessFromFile`; Java via google-auth `ServiceAccountJwtAccessCredentials`, and `MoreCallCredentials.from` converts an unscoped `ServiceAccountCredentials` into it.
- Service account OAuth credentials ([Google Call Credentials: Service Account OAuth Credentials](spec/10-vendor-specific/05-google-call-credentials.md#5-service-account-oauth-credentials)): Go `oauth.NewServiceAccountFromKey` / `NewServiceAccountFromFile`; Java via scoped google-auth `ServiceAccountCredentials`; not in C++.
- User refresh token credentials ([Google Call Credentials: User Refresh Token Credentials](spec/10-vendor-specific/05-google-call-credentials.md#6-user-refresh-token-credentials)): C++ `GoogleRefreshTokenCredentials`; Java via google-auth `UserCredentials`; Go only through ADC or an `oauth.TokenSource` wrapping an `x/oauth2` token source.
- External account credentials ([Google Call Credentials: External Account Credentials](spec/10-vendor-specific/05-google-call-credentials.md#7-external-account-credentials)): C++ `ExternalAccountCredentials` (file, URL, and AWS sources); Java and Go only through the auth library (ADC, google-auth `ExternalAccountCredentials`, or `x/oauth2/google`).
- IAM credentials ([Google Call Credentials: IAM Credentials](spec/10-vendor-specific/05-google-call-credentials.md#8-iam-credentials)): C++ only (`GoogleIAMCredentials`).
- GDCH service account credentials ([Google Call Credentials: GDCH Service Account Credentials](spec/10-vendor-specific/05-google-call-credentials.md#9-gdch-service-account-credentials)): C++ only (`GDCHServiceAccountCredentials`).
- Authentication library adapters ([Google Call Credentials: Authentication Library Adapters](spec/10-vendor-specific/05-google-call-credentials.md#11-authentication-library-adapters)): Java `MoreCallCredentials.from`; Go `oauth.TokenSource`; not in C++ (applications use a metadata credentials plugin).
- STS (RFC 8693) token exchange call credentials (generic, not part of section 10): C++ `experimental::StsCredentials` and Go `credentials/sts`; not in Java.
